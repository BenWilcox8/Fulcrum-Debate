# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

## Stack (fixed by the product owner)

- **Tauri v2** - native desktop shell (Rust), config in `src-tauri/`.
- **React + TypeScript + Vite** - front end in `src/`.
- **Tailwind CSS v4** - via the `@tailwindcss/vite` plugin; global styles are `@import "tailwindcss";` in `src/index.css` (no `tailwind.config.js`, no PostCSS config).
- **react-router-dom v7** - uses `HashRouter` (`src/App.tsx`) - `file://` context under Tauri has no server to resolve real paths.
- **Tiptap v3** - shared rich-text editor layer in `src/editor/`: factory (`core/`), marks (`marks/`), headings + outline (`headings/`), preset (`preset.ts`), React primitive (`react/`).
- **Yjs + y-indexeddb** - shared data types and local persistence.
- **XYFlow (`@xyflow/react` v12)** - the flow-sheet canvas in `src/flow/canvas/`.

The app is strictly **local-first**: nothing in the boot/render path may await a network resource.

## Commands

- `npm run tauri dev` - launch the native desktop window with hot reload.
- `npm run dev` - Vite front end only (browser, no shell).
- `npm run build` - type-check both tsconfigs then `vite build`.

## Hard product rule: local-first boot

Nothing rendered on startup (`main.tsx`, `App`, the router, `RootLayout`, or the default screen) may `await` a network resource.
Tauri IPC is local (not network) and is allowed on the boot path, but must degrade to sensible defaults so a slow read never blocks first paint.
Enforced by `src/App.offline-boot.test.tsx` - keep it green; if startup logic needs the network, the design is wrong.

## IPC command seam

Feature code calls Tauri via `src/ipc/` only - never `invoke` directly.

- Web half: `src/ipc/` - one typed wrapper per command.
- Rust half: `src-tauri/src/commands/` - every `#[tauri::command]`, registered via `generate_handler!` in `src-tauri/src/lib.rs`.
- **Gotcha - submodule re-export must be glob:** `commands/mod.rs` must use `pub use submodule::*;`, not a named re-export. `generate_handler!` needs the hidden `__cmd__*` items the macro emits; a named re-export fails to compile with `cannot find __cmd__<name>`.
- App commands need no ACL entry in `capabilities/default.json` - only plugin/core commands do.
- Tests mock `@tauri-apps/api/core` (real `invoke` requires the Tauri webview).

## Document service (the only entry point)

Feature code uses `openDocumentService()` from `src/documents/service` exclusively.
Never import `src/documents/core`, `src/documents/registry`, Yjs, or y-indexeddb directly from feature code.

- `create({kind,title})` / `open(id)` / `list()` / `rename(id,title)` / `remove(id)` / `close()` are the whole surface.
- `open(id)` returns a **cached handle** - deduplication lives in the service, not the core.
- Every method awaits local registry load (`whenReady`); nothing awaits the network.
- React integration: `DocumentsProvider` is mounted in `src/main.tsx` (outside `App`) so `App.offline-boot.test.tsx` never constructs a service. Use `useDocuments` / `useDocument(id)` from `src/documents/react`.
- **Gotcha - `useDocuments` must bail on a closed service.** `service.subscribe` throws synchronously on a closed service, so `useDocuments`'s effect guards `if (service.closed) return;` before subscribing (mirroring the dashboard's `useResumeDocuments`). Without it, a browser reload landing **directly** on a document screen (e.g. `/#/rounds/:id`) crashes the whole tree to a blank page: the screen's `useRounds` → `useDocuments` runs its subscribe effect during the window where `DocumentsProvider`'s StrictMode/remount swap has closed the old service but not yet provided the fresh one. The fresh service re-runs the effect, so the guard just skips the transient closed instance. `useDocument(id)` is already safe (it opens via the **async** `service.open`, whose rejection is caught). Regression pinned in `react.test.tsx` ("does not throw when the service in context is already closed").
- Tests use `fake-indexeddb/auto` + a fresh `IDBFactory()` per test (jsdom has no IndexedDB).

### Recent-documents query (`src/documents/registry/query.ts`)

`recentDocuments(source, query?)` is the synchronous, local-only read seam for recency surfaces (e.g. the launch dashboard's Resume/Recent zone). Re-exported from `src/documents/registry`.

- **Pure data seam.** It consumes a `Pick<DocumentRegistry, "list">` and returns `RegistryEntry[]`; no async, no I/O, no network. It does **not** re-sort - it rides `list()`'s documented last-edited-descending, stably tie-broken order (the same "never re-derive" discipline as the ToC), and filtering/capping preserve that order.
- **`RecentDocumentsQuery`** is `{ kind?, limit? }`. `kind` is one `DocumentKind` or an array (e.g. flow sheets *and* block files); omit for all kinds. `limit` caps to the most-recent N after filtering (non-positive/omitted = no cap).
- Because it reads only through `list()`, tests drive it with a real registry (fake-indexeddb) or a plain `{ list: () => entries }` stub. `query.test.ts` covers ordering, single/multi-kind filtering, the no-filter case, limit (alone and with a kind), empty registry, synchronicity, and the stub-source path.

### Namespaced preference store core

`src/preferences/store/` is the typed, namespaced preference store core - the pure, in-memory foundation feature settings sections register against (formatting, tools, shorthand config, ...). It is the first slice of the Settings Shell & Preferences Store feature; persistence and React bindings are follow-up slices that attach at its seams, so the core stays **free of React and Tauri imports**. It lives inside the existing `src/preferences` home (one coherent preferences module) and is re-exported from `src/preferences` and `src/preferences/store`.

- **The store:** `createPreferenceStore()` (`store.ts`) returns a `PreferenceStore` with `registerSection(definition)`, `getSection(id)`, and `listSections()` (registration order preserved for a stable settings UI). It is distinct from the theme `PreferencesProvider`/`usePreferences` (that is the Rust-owned single-shape app store over the IPC seam); this core is a general section registry with no persistence of its own; persistence is handled by the separate `openPreferenceStore()` wrapper in `persistence.ts`.
- **Sections are self-describing schemas.** A `SectionDefinition` is `{ id, title?, description?, fields }`; each `PreferenceField<T>` is `{ default, label?, description?, options? }`. The schema carries enough metadata (label/description/enumerated `options`) to render a settings control without the feature hand-wiring a form - the value type `T` is inferred from `default`. `SectionValues<S>` maps a schema to its concrete value object.
- **The handle:** `registerSection` returns a typed `SectionHandle<S>`: `get(key)` (falls back to the field default when unset), `set(key, value)` (immediate), `getAll()` (a snapshot), `reset()` (drops all overrides back to defaults), and `subscribe(listener)`. Only explicitly-set keys are stored, so `reset` is "forget the overrides". Reads/writes `clone` object values across the boundary (`structuredClone`; primitives pass through) so a mutated snapshot can never corrupt stored state - preference values are plain JSON-serializable data.
- **Subscription seam (the follow-up-slice attach point):** `subscribe(listener)` fires on every `set`/`reset` with the current snapshot and returns an unsubscribe; it does **not** fire immediately on subscribe (the snapshot is read separately via `get`/`getAll`), so it composes with `useSyncExternalStore` in the React-binding slice. Notifications are section-scoped - only that section's subscribers fire.
- **Duplicate registration is safe, never silent data loss.** Re-registering an id with a **structurally identical** schema (same keys and deeply-equal defaults; rendering metadata is ignored) is idempotent - it returns the existing live handle, preserving any values already set (survives StrictMode/hot-reload re-runs). Re-registering an id with a **different** schema throws a clear error naming the section, rather than clobbering data.
- **Tests:** `store.test.ts` follows the established behavioral pattern (no IndexedDB needed - the core is pure): defaults on unset reads, self-describing definition exposure, immediate set/read, section isolation, the subscribe/notify/unsubscribe seam (including no-immediate-fire and section-scoping), reset-to-defaults-with-notify, idempotent-vs-erroring duplicate registration, and snapshot immutability. Test section schemas omit `as const` so boolean/string defaults widen (a real feature widens a boolean default with `as boolean` when it needs to `set` the other value).

### Reactive React bindings for the store (`src/preferences/react/`)

The React binding layer over the store core; re-exported from `src/preferences`. It rides the store's own `subscribe` seam via `useSyncExternalStore` - never a second event system - and is separate from the theme `PreferencesProvider`/`usePreferences` (Rust-owned app store), which is untouched.

- **`PreferenceStoreProvider`** owns one app-lifetime `PreferenceStore` (created lazily, so the reference is stable), or adopts one passed via the `store` prop (tests, or a store already wired to persistence). `usePreferenceStore()` returns that shared store for a feature to `registerSection` against; it throws outside a provider.
- **`useSection(handle)`** returns the section's live typed `SectionValues<S>` snapshot and re-renders on any set/reset in that section. **`usePreferenceValue(handle, key)`** is a thin selector over it for one typed key. Hooks take a `SectionHandle` directly, so reactivity is fully decoupled from how the handle is distributed.
- **Gotcha - snapshot caching:** `getAll()`/`get()` allocate a fresh clone on every call, so `getSnapshot` must **not** call them directly (that reports a change every render and loops). `useSection` caches the snapshot and refreshes it only inside the `subscribe` listener (and once on (re)subscribe to catch a set that slipped in between render and effect), keeping the reference stable between notifications so React bails out when nothing changed.
- **Tests:** `react/react.test.tsx` covers typed defaults, live re-render on set/reset from elsewhere, stable-reference-between-notifications, unsubscribe-on-unmount, single-key selection, and the provider/`usePreferenceStore` sharing + outside-provider throw.

#### Local persistence (slice 2)

`src/preferences/store/persistence.ts` adds local persistence at the core's seams **without reworking it**: `openPreferenceStore()` wraps a fresh `createPreferenceStore()` and returns a `PersistentPreferenceStore` (the same registration surface plus `whenLoaded`, `loaded`, and `close()`). Re-exported from `src/preferences` and `src/preferences/store`.

- **Mechanism = y-indexeddb, mirroring the document registry.** The store holds arbitrary section x key JSON, a shape the fixed Rust `Preferences` struct behind the IPC seam cannot represent, so it uses one well-known Y.Doc (`PREFERENCES_DB_NAME = "fulcrum:preferences"`, a sibling of `fulcrum:registry`) bound by the same `IndexeddbPersistence` provider the document core uses. It is offline and free of React/Tauri, matching the core's constraint. `whenLoaded` reflects local IndexedDB read completion only - never the network - so it is not a boot blocker.
- **Only overrides are stored, never baked defaults.** Persistence derives what to write purely from the public seam (each field's `default` plus `getAll`): a key is written only when its value differs from the field default. Unset keys (and keys set back to default) store nothing, so they resolve to the registered default on reload - and a future default change flows through to any key the user never diverged.
- **Write** = subscribe to each section, rebuild that section's nested override map wholesale on every set/reset. **Read** = on `whenLoaded`, seed stored overrides back via `handle.set`, but skip any key the user already diverged during the load gap (never clobber an in-flight choice). Hydration snapshots the stored map first and suppresses re-persist while seeding, so a section cannot clobber its own not-yet-applied keys.
- **Tests:** `persistence.test.ts` uses `fake-indexeddb` (fresh `IDBFactory()` per test, same restart pattern as the registry) to prove real round-trips: set-survives-restart, unset-keys-still-default, object values, reset-forgets, no-clobber-during-load-gap, plus an offline block that stubs every network transport to throw.

## Settings screen shell (`src/settings/`)

The routed Settings screen and its contribution seam over the preference store. It is a UI layer only - it owns no preference data; sections and their values live on the shared `PreferenceStore` (`src/preferences`). `App` wraps the router in `PreferenceStoreProvider` + `SettingsProvider` (both pure/in-memory, so they are boot-path safe); the `/settings` route is registered in `AppRoutes` and linked from `RootLayout`'s primary nav.

- **A feature contributes one `SettingsContribution` = `{ definition, panel? }`** - the section schema to register plus the optional React panel that renders it. Add real feature contributions to `SETTINGS_CONTRIBUTIONS` (`contributions.ts`); the Evidence Formatting feature's panel is the first real contribution (wired via `formattingSettingsContribution`). The `demo` section (`src/settings/demo/`) remains as a reference example until it is retired. A contribution *without* a panel still appears as a navigable, resettable entry with a placeholder body.
- **`SettingsProvider({ contributions })`** registers every contribution's section against the `usePreferenceStore()` store (once, in a lazy `useState` initializer, so sections exist before the shell first calls `listSections()` - `registerSection` is idempotent, so a StrictMode/hot-reload re-run is safe) and exposes the panels by id via context (`useSettingsPanels`).
- **`SettingsScreen`** is master-detail: the left `<nav aria-label="Settings sections">` lists `store.listSections()` in registration order; the detail pane renders the active section's contributed panel (or the "no settings UI" placeholder) plus a **Reset to defaults** control that calls `handle.reset()` - section-scoped, so it restores that section only.
- **Gotcha - panel variance:** a `SettingsPanel<S>` consumes a `SectionHandle<S>`, so it is contravariant in `S`; a `SettingsContribution<SpecificSchema>` does not widen to the generic `SettingsContribution` on its own. Author contributions through **`defineSettingsContribution(...)`** - it type-checks the panel against its section schema at the definition site, then erases the generic (the shell only ever invokes a panel with its own section's handle, so the erasure is sound). The demo panel lives in its own file (`DemoSettingsPanel.tsx`), separate from the section-definition module, to satisfy `react-refresh/only-export-components`.
- **Tests:** `settings.test.tsx` covers section listing, default/selected panel render, panel switching (incl. the no-panel placeholder), live re-render on set, section-scoped reset, and the empty state; `settings-navigation.test.tsx` renders the real `App` to prove the route is reachable from the nav chrome and the shipped demo section renders its panel. `settings.e2e.test.tsx` is the whole-stack closeout: it contributes a section over a *persistent* store (`openPreferenceStore`), changes a value through the real `SettingsScreen` UI, asserts a separate consumer updates live, proves the override survives reopening a fresh store over the same y-indexeddb backend, and that reset restores the default (live and in storage).

## Dashboard home screen (`src/screens/DashboardScreen.tsx` + `src/screens/dashboard/`)

The prep-centric home rendered on the default index route. It renders synchronously from local data with no spinner or connecting state (upholds local-first boot). `DashboardScreen` is a thin composition of three zone components, in descending prominence:

- **`ResumeRecentZone`** (most prominent - an elevated bordered/shadowed card) fills its slot with recent resumable documents: it reads the live registry, narrows to the resumable kinds via the documents-layer `recentDocuments` query (riding its last-edited-descending order, never re-sorting), and renders each as a one-click `<Link aria-label="Resume {title}">` into its editor. **Routing map:** `flow-sheet` → `/rounds/{id}` (the round id *is* the flow-sheet document id); `block-file` → `/blocks` (the single workspace singleton). Other kinds (e.g. `speech-doc`) have no editor route yet and are omitted rather than linking nowhere. Empty registry → a plain empty-state card, never a broken zone.
  - **Gotcha - provider-optional reader:** the zone reads the document listing through a local `useResumeDocuments` hook that consumes `DocumentsContext` directly and *tolerates its absence* (returns `[]`, shows the empty state) rather than throwing like `useDocuments`. This is deliberate: `DocumentsProvider` lives in `main.tsx` *outside* `App`, so `App.offline-boot.test.tsx` renders a bare `App` with no provider (and no IndexedDB) to prove nothing on the boot path constructs a service. Degrading to empty keeps the dashboard painting there. The hook also guards `subscribe` with `service.closed` - during a StrictMode/remount swap a closed service can transiently sit in context, and `service.subscribe` throws on a closed service.
- **`StartSomethingNewZone`** is wired: `New round`, `New card`, `Open block file` buttons. **Gotcha - the dashboard is boot-path code, so this zone holds no document service** (the `DocumentsProvider` is mounted outside `App`; `App.offline-boot.test.tsx` renders `App` bare). - **`/rounds/new` (`NewRoundScreen`)** is the create-and-redirect seam: it `createRound()`s (off the boot path, so it *may* hold the service) and `navigate(..., { replace: true })`s to `/rounds/:id`. Declared as a static route *before* `rounds/:roundId`. This is the pattern any "create X from the dashboard" action should follow.
- **`LibraryNavZone`** is complete: `<Link>`s onto the existing `/blocks`, `/rounds`, and `/speeches` screens - every top-level content area a debater keeps work in.

Any test doing a global `getByRole("link", { name: /block file|rounds|speeches/i })` throws "multiple elements" - scope such queries to the primary nav via `within(screen.getByRole("navigation", { name: /primary/i }))`. `App.offline-boot.test.tsx` and `App.test.tsx` were updated this way; keep it.

## Fragment convention (Yjs shared-type layout)

Each document's content lives in named top-level Yjs shared types ("fragments") on `handle.doc`.
**A fragment name is bound to a Yjs type forever** - Yjs fixes the type on first access; re-typing or renaming a shipped fragment is a bug.
Reserved fragments:

| Kind | Fragment | Yjs type | Constant |
|---|---|---|---|
| `flow-sheet` | `columns` | `Y.Array<Y.Map>` | `FLOW_COLUMNS_FRAGMENT` |
| `flow-sheet` | `nodes` | `Y.Map<Y.Map>` | `FLOW_NODES_FRAGMENT` |
| `flow-sheet` | `contention:<nodeId>` | `Y.XmlFragment` | `contentionContentFragment(nodeId)` |
| `flow-sheet` | `subpoints` | `Y.Map<Y.Map>` | `FLOW_SUBPOINTS_FRAGMENT` |
| `flow-sheet` | `subpoint:<nodeId>` | `Y.XmlFragment` | `subpointContentFragment(nodeId)` |
| `flow-sheet` | `edges` | `Y.Map<Y.Map>` | `FLOW_EDGES_FRAGMENT` |
| `flow-sheet` | `rfd` | `Y.XmlFragment` | `FLOW_RFD_FRAGMENT` |
| `block-file` | `body` | `Y.XmlFragment` | `BLOCK_FILE_FRAGMENT` |
| `speech-doc` | `body` | `Y.XmlFragment` | `SPEECH_DOC_BODY_FRAGMENT` |

The `contention:<nodeId>` and `subpoint:<nodeId>` rows are each a **family** of per-node fragments, one `XmlFragment` per node keyed by its stable node id (not a single fixed name) - each contention's/subpoint's text is an independent Tiptap surface. Same "one fragment name binds to one type forever" rule applies: a given node id's name never re-types. The `subpoints` `Y.Map` is the subpoints' own membership/order store, a sibling of `nodes` (subpoints nest under a *contention*, not a column, so they live outside `nodes`).

## Shared editor layer

Feature editors consume exactly two things from `src/editor/`:
- **`editorPreset(options?)`** (`src/editor/preset.ts`) - the agreed extension bundle (bold + highlight + font-size + headings). Pass `extensions` and `headingLevels` options for feature-specific additions.
- **`DocumentEditor`** (`src/editor/react/`) - the editable React surface; takes a `DocumentHandle` + `fragment` name. `useDocumentEditor` is the hook form for callers that need the raw `Editor`.

**Never add a `History`/StarterKit undo extension.** The `Collaboration` binding already installs the Yjs undo plugin; a ProseMirror history extension creates a second conflicting stack.

Mark schemas are stable contracts (other tools read them): bold = `bold` mark (`<strong>`), highlight = `highlight` mark (`<mark>`, `multicolor: false`), font size = `textStyle` mark with `fontSize` attribute from `FONT_SIZE_SCALE`.

## Flow sheet

Three module groups, layered bottom-up:
- `src/flow/` - data substrate: column + node CRUD/observe helpers. Import the whole model surface from `src/flow`.
- `src/flow/canvas/` - XYFlow canvas (`FlowCanvas`), write strip (`ColumnControls`), composited panel (`FlowSheetPanel`). Import from `src/flow/canvas`.
- `src/rounds/` - a round *is* a `flow-sheet` document; `useRounds()` in `src/rounds/rounds.ts` is the whole seam.

Key gotchas:
- **Column reorder rebuilds** (safe - columns carry only primitives). Node reorder does not rebuild - nodes use a keyed `Y.Map` so attached rich content survives reorder.
- Column id becomes the XYFlow node id; flow nodes reference their column via `parentId = columnId`.
- Register node kinds via `FlowCanvas`'s `flowNodeTypes` prop (`FlowNodeRegistry`). An unregistered kind is skipped (no renderer), not an error.
- **Empty-round hint:** when a live `handle` has zero columns, `FlowCanvas` overlays a quiet centred "No speech columns yet / Add a column above (e.g. 1AC) to start flowing this round." message (gated on `handle != null` so it never flashes before the document opens; clears the moment the first column lands). It is positioned in the lower-centre (`top-[60%]`) so it stays clear of the timer widget pinned top-right.
- `src/test/setup.ts` installs a no-op `ResizeObserver` stub (jsdom ships none) - XYFlow requires it.
- **`RootLayout` must use `h-screen` (not `min-h-screen`) on its root div.** `min-h-screen` gives no definite CSS height, so `flex-1` descendants cannot distribute free space and `h-full` inside the canvas resolves to 0 - the XYFlow `ResizeObserver` always measures 0 and column heights stay at the fallback forever. `h-screen` + `overflow-hidden` on the root div give the whole flex chain a definite `100vh`, and `overflow-auto` on `<main>` lets content-heavy screens (Dashboard) still scroll when content exceeds the viewport.

### Contention container node (`src/flow/contention.ts` + `src/flow/canvas/`)

The first concrete flow-node kind: a large, rounded container a debater drops into a column while flowing by typing a `C#` trigger (`C1`, `C2`, ...), hosting an argument-text Tiptap surface. Slice 1/3 of the Contention & Subpoint Nodes PRD - subpoint nesting (slice 2/3) has landed; argument rows have also landed (see `argument-rows.ts`); collapsing and drag/strike remain. Model re-exported from `src/flow`; the canvas layer from `src/flow/canvas`.

- **Two-layer storage, both already owned - this module invents no new membership.** A contention *is* a `FlowNode` of kind `CONTENTION_KIND` (`"contention"`) in the `nodes` fragment (`addContention` is a thin named wrapper over `addNode`, `listContentions` a `listColumnNodes` filter), so it gets column-membership, ordering, reorder-safe identity and reload for free. Its **argument text** lives in its own top-level `XmlFragment` named `contentionContentFragment(nodeId)` = `contention:<nodeId>` - independent Tiptap surface per contention, keyed by the stable node id, so text survives reorder and reload and no two contentions share content.
- **Label is derived from rank, not stored.** A contention's `C#` header is its 1-based index among the column's contentions (`ContentionNode`'s `useContentionHeader` observes `observeNodes`/`observeColumns` and renumbers live). The trigger's typed number is only the *gesture* - in-order flowing (`C1`, `C2`, ...) reads naturally and a reorder relabels for free, so the model stays free of a stored number.
- **The C# trigger (keyboard-first, no dialog).** `parseContentionTrigger("C1")` → `1` (case-insensitive `^[Cc][1-9]\d*$`, 1-indexed, trims). `stepContentionTrigger(buffer, key)` (`contention-trigger.ts`) is the pure keystroke reducer: alphanumerics accumulate, **Enter commits** (fires the parsed number, so `C12` doesn't fire at `C1`), any other key abandons the token. `useContentionTrigger(handle, activeColumnId)` wires it to a **document-wide** keydown listener that **ignores editable targets** (`isContentEditable`/`INPUT`/`TEXTAREA` - so typing *inside* a contention or the column-label editor never spawns another), firing `addContention` on commit.
- **Active column routes the trigger.** Clicking a `SpeechColumnNode` sets the flow sheet's **active column** (a neutral `ring-2` shows which); the trigger only fires into that column. Selection state + the handle live on `FlowSheetContext` (`flow-sheet-context.ts` holds the context + `useFlowSheet`; `FlowSheetProvider.tsx` owns the component - split per the repo's context convention and to satisfy `react-refresh/only-export-components`). **Why the context:** XYFlow node `data` must be a plain record, so a node component cannot receive the live `DocumentHandle` through it - the context carries the handle (for `ContentionNode`'s editor + rank) and the active-column setter out-of-band. `useFlowSheet` is provider-tolerant (returns `null`), so a bare canvas still paints. **Stale-column guard:** `FlowSheetProvider` subscribes to `observeColumns` and clears `activeColumnId` when the active column is deleted; `useContentionTrigger` additionally guards the `addContention` call with `getColumn` so a trigger that races a deletion is a no-op, never an error.
- **Wiring.** `FlowSheetPanel` wraps its `ColumnControls` + `FlowCanvas` in `FlowSheetProvider`, installs `useContentionTrigger`, and passes `CONTENTION_FLOW_NODE_REGISTRY` as `flowNodeTypes` - so `RoundScreen` (which renders `FlowSheetPanel`) gets contentions with no further wiring. `CONTENTION_NODE_HEIGHT = 160` (a taller slot than the default flow-node height) is the "large" in the container.
- **Designed for nesting (achieved).** A contention is addressed purely by node id and its content fragment is derived from that id; subpoints add their own membership/content keyed off the same id without changing this contract - exactly as this module layered onto `nodes` without changing that contract.
- **Tests:** `contention.test.ts` (`fake-indexeddb`) covers `parseContentionTrigger` accept/reject, node-scoped fragment naming, `addContention`/`listContentions`, and a real close/reopen round-trip (membership + argument text survive). `contention-trigger.test.ts` drives the pure reducer as keystroke transitions. `ContentionNode.test.tsx` renders through the real `FlowCanvas` + `FlowSheetProvider` (large/rounded/side-coloured container, rank labelling `C1`/`C2`, the mounted ProseMirror surface). `contention-flow-sheet.test.tsx` drives the whole trigger seam through `FlowSheetPanel` (click column → type `C1`+Enter → contention appears and persists; successive `C1`/`C2`; no-op with no active column; no-op when active column is deleted before trigger commits).

### Subpoint container node (`src/flow/subpoint.ts` + `src/flow/canvas/`)

The second concrete flow-node kind and slice 2/3 of the Contention & Subpoint PRD: a small, **dark, visually-nested** container a debater drops *inside* a contention by typing an `S#` trigger (`S1`, `S2`, ...) while flowing, hosting its own Tiptap text surface. It layers onto the Contention container exactly as the contention layered onto `nodes` - without changing the contention contract. Model re-exported from `src/flow`; the canvas layer from `src/flow/canvas`.

- **Nesting is enforced at the write seam, not by convention.** A subpoint belongs to a *contention*, not a column: its membership foreign key is a contention's node id, and `addSubpoint(handle, contentionId)` **throws** unless that id resolves to a live `CONTENTION_KIND` node. There is no API to mint a subpoint free of a parent, so "subpoints only exist inside a contention" is a real invariant. (Contrast `addNode`/`addContention`, which do *not* validate `columnId` - an orphan node is merely unrendered; a subpoint cannot be born an orphan.)
- **Its own two-layer storage, mirroring the contention (sibling fragments, not `nodes`).** Membership + order live in a *new* top-level `subpoints` `Y.Map<Y.Map>` keyed by subpoint id (fields `id`, `contentionId`, `order`) - a sibling of `nodes`, since subpoints nest under a contention rather than a column. Text lives in the subpoint's own `XmlFragment` `subpointContentFragment(id)` = `subpoint:<id>` (the `subpoint:` prefix can never collide with a contention's `contention:` content). The keyed map (not an array) keeps a future reorder from rebuilding a subpoint's map. `listSubpoints(handle, contentionId)` returns a contention's subpoints in order (rank → the `S#` label); `getSubpoint`/`removeSubpoint`/`observeSubpoints` round out the seam.
- **Label is derived from rank, not stored** (same as the contention's `C#`): `SubpointNode`'s `useSubpointHeader` observes `observeSubpoints` and renumbers `S1`/`S2` live, so in-order flowing reads naturally and a reorder relabels for free.
- **The S# trigger fires from *inside* the contention's editor - the opposite of C#.** The C# contention trigger is document-wide and deliberately *ignores* editable targets; the S# trigger must fire *within* a contention's editable Tiptap surface (that is what "inside a contention" means). `useSubpointTrigger(handle, contentionId, editor)` listens in the **capture phase on `document`** and acts only when the keystroke's target is inside *this* contention's editor DOM (`editor.view.dom.contains(target)`). Capturing on `document` guarantees the handler runs **before** ProseMirror's own keydown handling, so a committed Enter is cancelled (`preventDefault` + `stopImmediatePropagation`) before it splits a paragraph, and the just-typed `S1` is stripped back out (`stripTypedToken` deletes the token only when the text immediately before the caret is *exactly* it - so under jsdom, where keydown inserts nothing, the strip is a safe no-op and the subpoint is still created). The pure reducer `stepSubpointTrigger` mirrors `stepContentionTrigger` (Enter commits, non-alphanumeric abandons); the commit is additionally `getNode`-guarded so a trigger racing the contention's deletion is a no-op, not a throw.
- **`ContentionNode` owns the raw editor via `useFlowNodeEditor`.** To let the trigger intercept keystrokes and strip the token, `ContentionNode` uses `useFlowNodeEditor` + `EditorContent` (the raw `Editor` instance) instead of the `DocumentEditor` component. Its body region renders the argument `EditorContent`, then the nested `SubpointNode`s below it (via `useContentionSubpoints` over `observeSubpoints`); the body is `overflow-y-auto` so subpoints scroll within the fixed-height container. `SubpointNode` is dark (`bg-shell-text` + light text) and indented (`ml-4`/`pl-3` + a `border-l-2` rail) so the hierarchy is obvious; it reads the handle from `FlowSheetContext` (provider-tolerant) and uses `useFlowNodeEditor` + `EditorContent` to bind its editor to `subpointContentFragment(id)`. No `FlowSheetPanel`/wiring change was needed - the panel already renders `ContentionNode` via `CONTENTION_FLOW_NODE_REGISTRY`.
- **Designed for argument rows (now landed) and the next slices (collapsing, drag/strike) the same way the contention was.** A subpoint is addressed purely by id and its content fragment is derived from that id, so those PRDs build on both containers without changing this contract.
- **Tests:** `subpoint.test.ts` (`fake-indexeddb`) covers `parseSubpointTrigger` accept/reject (incl. rejecting `C1`), node-scoped fragment naming (distinct from `contention:`), `addSubpoint` nesting enforcement (throws on missing/non-contention parent), `listSubpoints` ordering + per-contention scoping, `removeSubpoint`, and a real close/reopen round-trip (nesting + text survive). `subpoint-trigger.test.ts` drives the pure reducer as keystroke transitions. `SubpointNode.test.tsx` renders through the real `FlowCanvas` (nested inside the contention body, dark+indented class hooks, rank labelling `S1`/`S2`, the mounted ProseMirror surface). `subpoint-flow-sheet.test.tsx` drives the whole trigger seam through `FlowSheetPanel` (type `S1`+Enter *into the contention's editor* → nested subpoint appears and persists; successive `S1`/`S2`; no-op when contention is deleted before trigger commits; no-op on a non-trigger token).

### The container contract, end to end (slice 3/3) + closeout e2e

The **Contention & Subpoint Nodes** PRD is complete. The container contract the remaining flow PRDs (collapsing, drag/strike; argument rows have landed) build directly on is a short pointer:

- **A container is a node addressed purely by a stable id, with its text in an id-derived fragment.** A contention is a `FlowNode` of `CONTENTION_KIND` in the `nodes` fragment (`addContention`/`listContentions` over `src/flow/nodes`); a subpoint is a record in the sibling `subpoints` `Y.Map` keyed by id, whose `contentionId` is its nesting foreign key (`addSubpoint`/`listSubpoints`/`observeSubpoints` over `src/flow/subpoint`, nesting enforced at the write seam). Each container's editable text is its own top-level `XmlFragment` derived from that id - `contentionContentFragment(id)` / `subpointContentFragment(id)` - so text survives reorder + reload and no two containers share content. **A new nested/attached kind (rows, etc.) layers on the same way both of these did: its own membership store keyed off the parent's id + its own id-derived content fragment, without changing this contract.**
- **Labels (`C#`/`S#`) are derived from rank, never stored** - the canvas renumbers live off `observeNodes`/`observeSubpoints`, so a reorder relabels for free. Any future ordering feature keeps the model free of a stored number.
- **The keyboard trigger is the create gesture, no dialog.** C# is document-wide and *ignores* editable targets; S# fires from *inside* a contention's own editor (capture-phase on `document`, scoped to that editor's DOM). Build on `useContentionTrigger`/`useSubpointTrigger`; the panel (`FlowSheetPanel`) already wires both.
- **Closeout e2e:** `contention-subpoint.e2e.test.tsx` composes the whole stack the way the app ships it (round seam → `FlowSheetPanel` → C#/S# triggers → per-node Tiptap text), then proves the structure + text survive a fresh-instance service reload (mirrors the `flow-sheet.e2e` restart precedent). **Test gotcha - jsdom does not implement `HTMLElement.isContentEditable`,** so the document-wide C# listener cannot tell a keystroke was aimed at a contention's editor and folds it into its token buffer (a real browser reports `true` and the trigger ignores it). Drive all C# gestures *before* any editor typing (build the contentions, then nest the subpoints) to keep the keyboard flow faithful without tripping that gap.

### Node collapsing (`src/flow/canvas/flow-collapse.ts` + `useFlowCollapse.ts` + `useCollapseHotkey.ts`)

Collapse view-state for the flow containers (contentions and their nested subpoints), the collapsing track of the Argument Rows & Collapsing PRD. A debater collapses a container to a single low horizontal bar to keep a densely-flowed sheet legible, and collapses everything but the one they are working on in one gesture. Chrome + view-state only - it never touches the flow document or the container editors (a sibling task owns argument-row semantics inside those editors).

- **Collapse is transient view-state, by design (reload resets it).** Collapse/expand and the active node are ephemeral React state held by `useFlowCollapse(handle)` and exposed on `FlowSheetContext.collapse` (a `FlowCollapseState`); **nothing is persisted to Yjs**, so reopening a round always starts fully expanded. This is deliberate - a collapse choice is a moment-to-moment reading aid tied to the argument on screen right now, not a property of the case worth surviving a reload, and keeping it out of the shared types means it never syncs or conflicts. A durable "remember my layout" mode, if ever wanted, is a new opt-in on top of this seam, not a change to the default.
- **"Active" is well-defined.** The **active node** is the container the debater is currently working in: the one whose header was last clicked or whose Tiptap surface was last focused (`ContentionNode`/`SubpointNode` call `collapse.setActiveNodeId` on header click and editor `onFocus`). "Collapse All Except Active" keeps that node - and, if it is a nested subpoint, its ancestor contention so the active node stays visible - expanded and collapses every other container; with no active node yet it collapses everything.
- **Two pure pieces (`flow-collapse.ts`), testable without React.** `collapseTargets(allNodeIds, activeNodeId, parentOf)` is the pure reducer: it returns every id to collapse = all ids minus the active node's ancestor chain (walked via `parentOf`, which maps a subpoint id → its contention; a contention has no parent). `readFlowContainerTree(handle)` is the live handle read that enumerates the collapsible containers (`listNodes` filtered to `CONTENTION_KIND`, plus each contention's `listSubpoints`) and builds `parentOf`. `useFlowCollapse` composes them: single-node `toggleCollapsed`/`setCollapsed`, `setActiveNodeId`, and `collapseAllExceptActive()` (reads the tree at call time so it always reflects the current sheet).
- **The collapsed bar reflows the column - additive layout, not a rebuild.** `flowNodesToNodes(groups, registry, { collapsedIds })` gained an optional third arg: a node whose id is in `collapsedIds` lays out at `COLLAPSED_NODE_HEIGHT` (40px, a single bar) instead of its kind's slot height, and the nodes below it in the column reflow up. `useFlowNodes(handle, registry, collapsedIds)` threads the set; `FlowCanvas` reads `useFlowSheet()?.collapse.collapsedNodeIds` (provider-tolerant - a bare render-only canvas collapses nothing). Subpoints render as React children inside a contention's body (not XYFlow nodes), so a subpoint collapse is pure React (its editor is hidden) and never touches XYFlow layout.
- **The two entry points.** The global **Ctrl+\\** hotkey (`useCollapseAllExceptActiveHotkey`, installed by `FlowSheetPanel`) - a document-wide listener that, *unlike* the C# trigger, fires regardless of the focused target because the debater's caret is inside the active node when they reach for it. And a discoverable **Collapse all except active** button in the panel's toolbar strip (tooltip names the hotkey). Both call `collapse.collapseAllExceptActive()`.
- **Header = collapse toggle.** Each `ContentionNode`/`SubpointNode` header is a `<button aria-expanded>` that toggles that node's collapse (and marks it active); the container carries `data-collapsed` when collapsed and drops its body. Contention bars keep the side colour + border; subpoint bars keep the dark indented treatment - so a collapsed node still reads as belonging to the flow's visual language.
- **Stale-activeNodeId guard:** `useFlowCollapse` exposes `clearActiveNodeIfAbsent(liveIds)`, and `FlowSheetProvider` subscribes to `observeNodes` + `observeSubpoints` and calls it on every change - mirroring the existing stale-column guard (`observeColumns` clears `activeColumnId`) so a deleted container never stays "active".
- **Tests:** `flow-collapse.test.ts` covers the pure reducer (collapse-all-when-no-active, keep-active + ancestor chain, empty) and `readFlowContainerTree` (enumeration + parent map). `useFlowCollapse.test.tsx` drives the hook over a real handle (toggle/set, active tracking, collapse-all-except-active for a contention, a nested subpoint's ancestor, and the no-active case). `node-host.test.ts` adds the collapsed-slot reflow. `collapse-flow-sheet.test.tsx` drives the whole seam through `FlowSheetPanel` (header-click collapse→bar→expand for a contention and a subpoint, the button, and Ctrl+\\; **`findByTestId` throws on multiple contentions - use `findAllByTestId`**).

### Argument rows inside a box (`src/flow/argument-rows.ts`)

The **argument-row** semantics inside a flow-node's Tiptap surface (a contention *or* a subpoint): the schema that turns a box's editor content into stacked *argument rows*, each grouping one or more *responses* separated by dividers, plus the Enter / Shift+Enter transitions that build them. Rows track of the **Argument Rows & Collapsing** PRD (a sibling task builds node *collapsing* view-state on the same containers - kept scoped to the row/response semantics). Re-exported from `src/flow`.

- **Schema = two enforced container node types under the box's `doc`.** The box's content fragment (`contention:<id>` / `subpoint:<id>`) is one editor whose top node is overridden to `argument+`; `argument` (`ARGUMENT_NODE_NAME`) is `response+`; `response` (`RESPONSE_NODE_NAME`) is `paragraph+`. So a box always holds ≥1 argument row, each row ≥1 grouped response - the grouping is enforced structure, not convention, exactly like the block-file side division and card anatomy. Both container types are `defining` and kept out of every group (only reachable by name), so a response can never appear loose in the box and an argument can never nest inside a response. `flowArgumentDocument` is a `doc` override (the intentional "Duplicate extension names: ['doc']" warning, same as the block-file `doc`). Installed via `argumentRowExtensions` + `argumentRowKeymap` through the shared preset's feature-extension seam.
- **The two gestures are plain structural splits at two depths** (`splitFlowRow` via `canSplit`/`tr.split`): **Enter → `newArgumentRow`** splits at the *argument* depth (a new top-level row, its own response group, caret moved into it, trailing text carried along - natural editor feel); **Shift+Enter → `newGroupedResponse`** splits at the *response* depth (a new response appended to the **current** argument, staying in the same box/group). Both are plain `(editor) => boolean` helpers *and* bound by `argumentRowKeymap` (priority `1000` so its `Enter` wins over the editor's baseline block-split, falling through to `false` when the caret is not inside a row). **Keep the key-event contract clean - the Shorthand Engine PRD hooks the same Enter / Shift+Enter transition later** by wrapping `newArgumentRow`/`newGroupedResponse` rather than re-deriving the split.
- **Addressability for the drag/strike PRD.** `locateArgumentRows(doc)` is the pure, position-only locator (no editor, nothing to invalidate - re-derive after edits, the card-unit discipline): one `ArgumentRowSpan` per row (`{ node, from, to, responses }`), each `ResponseSpan` being `{ node, from, to }`. This is the seam that later PRD targets to move or strike a specific argument *or* an individual response. The grouping persists in the flow doc (it *is* the fragment content) and reloads intact.
- **Divider rendering = data hooks + CSS, schema ships no CSS.** Each node serializes with `data-flow-argument` / `data-flow-response`; the divider *between* adjacent responses is a single sibling-combinator rule in `src/index.css` (`[data-flow-argument] > [data-flow-response] + [data-flow-response]` → `border-top: 1px solid var(--color-shell-border)`), matching the flow's existing `shell-border` divider language.
- **Wiring.** `ContentionNode` and `SubpointNode` both pass `FLOW_ARGUMENT_PRESET` (`src/flow/canvas/flow-argument-preset.ts` - its own module, a **stable** preset reference shared by both, kept out of the component files to satisfy `react-refresh/only-export-components` and avoid a circular import). The contention's S# subpoint trigger composes cleanly: it cancels a *committed* `S1`+Enter in the capture phase before ProseMirror sees it, so only a non-`S#` Enter falls through to the argument-row keymap.
- **Load-time migration for legacy bare-paragraph content (`migrateFlowNodeFragment`).** Documents written before argument rows landed have fragments whose top-level children are bare `<paragraph>` elements. `migrateFlowNodeFragment(doc, fragment)` detects that shape (all children are `paragraph` elements, none is already an `argument`) and wraps each paragraph in `<argument><response>...</response></argument>` in a single Yjs transaction before the editor binds, so existing text survives under the new schema rather than being discarded by `createAndFill`. It is a no-op on an empty fragment or one already in the argument-row shape. Re-exported from `src/flow`.
- **`useFlowNodeEditor` (`src/flow/canvas/useFlowNodeEditor.ts`).** Replaces `useDocumentEditor` for flow-node text surfaces (both contention and subpoint). It runs `migrateFlowNodeFragment` on the fragment *before* creating the editor so y-tiptap never sees the legacy shape. Lifecycle mirrors `useDocumentEditor` (one editor per handle+fragment, rebuilt on change, destroyed on unmount); returns `null` until the handle is locally loaded.
- **Tests:** `argument-rows.test.ts` (`fake-indexeddb`, real editor over a flow-sheet fragment) covers the auto-filled initial box, Enter→new row / Shift+Enter→grouped response (direct-command *and* live `fireEvent.keyDown` proving the keymap wins over the baseline Enter), the `data-flow-*` divider hooks, the keymap binding shape, `locateArgumentRows` cross-checked against an independent walk, and a close/reopen round-trip proving the grouping stays addressable.

### The Enter / Shift+Enter key-event contract (short pointer)

The one keyboard contract inside a flow-node box, and the seam the **Shorthand Engine PRD** hooks:

- **Enter → `newArgumentRow`** (new top-level argument row) and **Shift+Enter → `newGroupedResponse`** (new grouped response in the *current* argument) - both plain `(editor) => boolean` split helpers in `src/flow/argument-rows.ts`, bound by `argumentRowKeymap` (priority `1000`, so its Enter wins over the editor's baseline block-split and falls through to `false` when the caret is not inside a row).
- **The Shorthand Engine hooks this same transition by wrapping `newArgumentRow` / `newGroupedResponse`, never re-deriving the split** - so the two commands stay the single source of truth for "what Enter / Shift+Enter do in a box". Keep the keymap binding-only (the work lives in the two commands) so a later feature can compose on top without forking the keymap.
- A committed `S#` subpoint trigger is cancelled in the capture phase *before* ProseMirror (and therefore this keymap) sees the Enter, so only a non-`S#` Enter reaches the argument-row transitions - the two gestures compose cleanly.

## Shorthand engine (`src/shorthand/`)

The abbreviation→expansion dictionary + the expansion engine that rewrites abbreviations in just-completed text at a box/argument transition (Shorthand Engine PRD).
Slice 1/2 is **model + engine** (dictionary + transition-time expansion, below); slice 2/2 is the **flow-surface wiring + surface-generic scope gate** (see "Flow wiring & scope gate" below). Management UI + team sync are a separate PRD (SH2).
The engine operates on shared Tiptap core text and is deliberately surface-agnostic (no argument-row or dictionary-persistence coupling), so the flow surface now and a speech-doc surface later invoke it the same way on *their* transition event.
Re-exported from `src/shorthand`.

- **The dictionary (`dictionary.ts`).** `openShorthandDictionary()` returns a `ShorthandDictionary` (`lookup`/`set`/`remove`/`entries`/`subscribe`/`whenLoaded`/`loaded`/`closed`/`close`), persisted through **the same y-indexeddb pattern as the registry / preference store** - one well-known Y.Doc under `SHORTHAND_DB_NAME = "fulcrum:shorthand"`, a top-level `Y.Map<string>` keyed by abbreviation → expansion. Offline, React/Tauri-free, `whenLoaded` = local IndexedDB read only (never a boot blocker). **Matching is exact + case-sensitive** (`lookup` is a bare `map.get`), which is what makes expansion non-surprising: the engine feeds it one whole token at a time, so a substring or wrong case can never resolve. `lookup` is a bound closure, so it *is* a valid `ShorthandLookup` - pass `dict.lookup` straight to the engine. `set` rejects an empty abbreviation/expansion. `DEFAULT_SHORTHAND_ENTRIES` + `seedShorthandDictionary(dict, entries?)` are **fixtures only** (idempotent, never clobbers a user entry, not auto-applied on open) - there is no management UI yet, so a surface/test seeds explicitly.
- **The engine (`expand.ts`).** Two layers, both pure-token-only:
  - **`expandText(text, lookup)` (pure over a string)** → `{ text, changed }`: rewrites every *whole* word token that has a different expansion, copying separators verbatim. A **token** is a maximal run of `[\p{L}\p{N}]+` (`TOKEN_PATTERN`), so punctuation/whitespace are separators (`aff.` → `affirmative.`) and a partial/substring token (`affs`, `aff` inside `affluent`) is left untouched. Directly testable without an editor.
  - **`expandCompletedText(editor, lookup)` (ProseMirror command)** expands the **textblock the caret currently sits in** - the just-completed block. It scans that block's text nodes into concatenated text + a per-character offset→absolute-position map (`nodesBetween`, skipping non-text inline nodes so a token never spans one), tokenizes, and replaces each matched token via `tr.insertText(expansion, from, to)` **right-to-left** (so earlier positions stay valid) in one transaction/undo step; each replacement inherits the marks at its start position, so styled/surrounding text is preserved. No-op (`false`, no dispatch) when not in a textblock or nothing resolved to a different expansion.
- **The transition seam = `expandThen(editor, lookup, transition)`.** Runs `expandCompletedText` then invokes the surface's own transition command and returns *its* result (expansion is a best-effort side effect, never suppresses the transition). This is how the engine hooks a surface **without wiring the keymap** (the actual `argumentRowKeymap` wiring is the next slice): the flow surface will pass `newArgumentRow` / `newGroupedResponse` (`src/flow/argument-rows`); a speech-doc surface later passes its own split. **Runs exactly at the transition, never per keystroke** (see the Enter/Shift+Enter contract above) - expanding mid-word would fight typing and could corrupt a longer token.
- **Tests:** `dictionary.test.ts` (`fake-indexeddb`, fresh `IDBFactory` per test) covers exact/case-sensitive lookup, set/overwrite/remove, sorted `entries`, empty-input rejection, subscribe notify/unsubscribe, a real close/reopen round-trip (set *and* removal survive), and the seed fixtures (default seed, idempotent non-clobber, explicit set). `expand.test.ts` covers `expandText` (whole-token, multi-token+separators, substring/partial/wrong-case untouched, punctuation-adjacent, no-op/idempotent/empty cases) and the editor layer over the **exact argument-row composition the flow surfaces ship** (`argumentRowExtensions` + `argumentRowKeymap` on a real flow-sheet fragment): expansion of the just-completed block, substrings untouched, only-the-caret's-block (sibling rows untouched), mark preservation, the no-op-no-dispatch case, and `expandThen` composing with both `newArgumentRow` and `newGroupedResponse` (completed row expands, freshly typed row does not) incl. the transition still running when nothing expanded.

### Flow wiring & scope gate (slice 2/2, `scope.ts` + `preferences.ts` + `runtime.ts` + `react/`)

Slice 2 wires the engine onto the flow surface's argument-row transitions and gates it by a persisted, **surface-generic** scope preference. It is deliberately layered so a speech-doc surface (built in parallel) adopts the identical gate + runtime seam without any engine change. Model re-exported from `src/shorthand`; the React bindings from `src/shorthand/react` (kept out of the model index, like `src/formatting/react`).

- **The scope gate (`scope.ts`, pure + total).** `ShorthandScope` = `"both" | "flow" | "speech" | "neither"` (`DEFAULT_SHORTHAND_SCOPE = "both"` - a debater who enables shorthand generally wants it everywhere); `ShorthandSurface` = `"flow" | "speech"`. `isShorthandEnabledForSurface(scope, surface)` is the **whole** decision: `"both"`→every surface, `"neither"`→no surface, a surface-named scope→only the matching surface. **Surface-generic by construction:** the only surface-specific input is the passed key, so a new surface is gated correctly the moment it calls this with its own identity (add the identity to `ShorthandSurface`, and a matching `ShorthandScope` value + `SHORTHAND_SCOPES` entry if it wants to be independently selectable).
- **The scope preference (`preferences.ts`).** `registerShorthandSection(store)` registers section id `"shorthand"` (`SHORTHAND_SECTION_ID`) with one enumerated `scope` field (`SHORTHAND_SCOPE_KEY`, default `"both"`, `options: SHORTHAND_SCOPES`) on the shared `PreferenceStore` - same pattern as the formatting section. Idempotent; `readShorthandScope(handle)` reads it. Surfaced on the Settings screen via `shorthandSettingsContribution` (`src/settings/shorthand/shorthandSettings.ts`) → the generic `SchemaSettingsPanel` renders the scope select straight from the field's `options` (no bespoke panel), and it is spread into `SETTINGS_CONTRIBUTIONS`.
- **The runtime seam (`runtime.ts`) is how a surface runs scope-gated expansion without a per-editor preset.** The flow editor is built once from a **stable** module-level preset (`FLOW_ARGUMENT_PRESET`), so the live `{ lookup, enabled }` pair *cannot* be baked into it. Instead `shorthandRuntimeExtension` declares a `shorthand` slot on `editor.storage` (a `ShorthandRuntime`, disabled by default), a React binding pushes the live values into it (`setShorthandRuntime`), and the surface's transition keymap reads it *at keystroke time* via `expandTransition(editor, transition)` - which composes the engine's `expandThen` with the runtime: it expands the completed text first **only when `enabled && lookup`**, else runs the transition unchanged, always returning the transition's own result. The editor stays stable; the runtime updates in place. (`editor.storage` is typed as a fixed `Storage` interface, so accessing the dynamic slot needs a `Record<string, unknown>` widening - `storageOf`.)
- **Flow keymap = `flowShorthandRowKeymap` (`src/flow/canvas/flow-shorthand-keymap.ts`), which REPLACES `argumentRowKeymap` in `FLOW_ARGUMENT_PRESET`.** It binds the same Enter / Shift+Enter (priority 1000) but routes each through `expandTransition(this.editor, newArgumentRow | newGroupedResponse)` - **wrapping** the two transition commands per the argument-row key-event contract (never re-deriving the split), so those commands stay the single source of truth. `argumentRowKeymap` itself is unchanged and still used by `argument-rows.test.ts` and any surface that wants the un-hooked transitions. A committed `S#` subpoint trigger is cancelled in the capture phase *before* ProseMirror (and this keymap) sees the Enter, so only a non-`S#` Enter reaches expansion - the two gestures compose cleanly.
- **React wiring.** `ShorthandProvider` (mounted in `main.tsx` **outside `App`**, exactly like `DocumentsProvider`, so `App.offline-boot.test` renders a bare `App` that constructs no dictionary) opens the app's single `ShorthandDictionary`, **seeds the default abbreviations** on `whenLoaded` (idempotent/non-clobbering; the interim populate until SH2 management UI - the one place to reconsider), and provides its stable `lookup`. `useSurfaceShorthand(editor, surface)` is the **one call a surface makes**: it reads the live lookup (`useShorthandDictionary`, provider-tolerant → `null`), the live scope (`useShorthandScope`, provider-tolerant → `"both"`, riding `usePreferenceValue`), computes `enabled = isShorthandEnabledForSurface(scope, surface)`, and pushes `{ lookup, enabled }` onto the editor. `ContentionNode` and `SubpointNode` both call `useSurfaceShorthand(editor, "flow")`; a speech surface later calls it with `"speech"`.

### Cross-application drag-and-drop (`src/flow/edges.ts` + `src/flow/cross-apply.ts` + canvas drag)

Slice 1/3 of the **DnD/Strike** PRD: dragging a contention (an argument) onto another column drops a **copy** there - the original stays put - and records a **transparent arrow** edge from the original to the copy. Copies and arrows persist in the flow doc and reload intact. Strike-on-drop (slice 2/3) has landed - see the strike section below; the drop handler was written so the adjacency case could extend it, which it now does.

- **Edges are a new orthogonal flow-doc layer (`edges.ts`).** A `FlowEdge` (`{ id, sourceNodeId, targetNodeId, kind }`) lives in the new top-level `edges` `Y.Map<Y.Map>` fragment (`FLOW_EDGES_FRAGMENT`), a sibling of `nodes`/`subpoints` - keyed by id so removal/reorder never rebuilds a map, mirroring those stores. Endpoints are node ids; **incident edges are cascade-deleted when a node is removed** (`removeEdgesForNode` is called inside `removeNode`'s transaction) so orphan edges never accumulate. The only kind so far is `CROSS_APPLICATION_EDGE_KIND` (`"cross-application"`); the field exists so future edge kinds cost no schema change. Seam: `addEdge`/`listEdges`/`getEdge`/`removeEdge`/`removeEdgesForNode`/`observeEdges`, re-exported from `src/flow`.
- **The copy is a true, independent copy (`crossApplyContention(handle, nodeId, targetColumnId)`).** It mints a fresh contention in the target column (`addContention`) and **deep-clones** (Yjs `item.clone()` per top-level child) the source's argument-row content fragment into the copy's own id-derived `contention:<newId>` fragment - so the copy's addressable arguments/responses (`locateArgumentRows`) match at copy time then diverge (editing one never touches the other). Nested subpoints come across too: each is re-created under the copy (fresh id, order preserved) with its `subpoint:<id>` text deep-cloned. It records the arrow edge original→copy. The whole thing is **one `doc.transact`** (atomic, one undo step). Throws unless `nodeId` resolves to a live `CONTENTION_KIND` node - only a contention can be cross-applied. Re-exported from `src/flow`.
- **Draggability rides the node-host registry.** `FlowNodeTypeDefinition` gained an optional `draggable?: boolean`; a `true` kind is XYFlow-draggable **and drops its `extent: "parent"` clip** (so it can be dragged onto another column - a clipped node never could), keeping `parentId` for visual membership. `CONTENTION_FLOW_NODE_TYPE` sets `draggable: true`. Default kinds stay render-only (`draggable:false` + `extent:"parent"`), so existing node-host behaviour is unchanged.
- **The canvas owns the drag, never the mutation (`FlowCanvas`).** It runs **controlled** nodes now (`useState` seeded from the document-authoritative layout + `applyNodeChanges` via `onNodesChange`) so a drag is smooth, re-syncing to the doc layout whenever the model changes (`useEffect([docNodes])`) - which both snaps a dropped node back (the source only *copies*, never moves) and drops a newly-copied node into place. On `onNodeDragStop` it resolves the target column purely (`resolveNodeDropColumn` / `columnAtX` in `flow-drag.ts`: project the dragged child's center into absolute canvas x via `sourceColumn.x + node.position.x + width/2`, find the containing column; a gap → `null` → no copy) and calls the new `onNodeCrossColumnDrop?(nodeId, from, to)` prop **only when the target differs from the source**; then always `setNodes(docNodes)` to snap back. The canvas stays a pure view - `FlowSheetPanel` supplies the handler that calls `crossApplyContention`.
- **Edges render as the transparent arrow.** `useFlowEdges` observes `edges` and maps via pure `flowEdgesToEdges` (`flow-edge.ts`) to XYFlow edges: `opacity 0.35` (`CROSS_APPLICATION_EDGE_OPACITY`), muted stroke, `ArrowClosed` marker, non-selectable/non-focusable. `ContentionNode` renders two invisible `<Handle>`s (source Right, target Left, `isConnectable={false}`, opacity-0) purely as edge anchors - XYFlow needs handles to draw between nodes; they are not interactive (the canvas keeps `nodesConnectable={false}`).
- **Testing reality - drag needs a real browser; edges need real measurement.** XYFlow's node drag is d3-drag@3, which binds **mouse** events (`mousedown`/`mousemove`/`mouseup` on `window`, `view: window` required or it throws `null.document`), *not* pointer events - synthetic pointer events and the `chrome-devtools-axi drag` command (which only jiggles past the 1px `nodeDragThreshold`, no traversal) do **not** move a node; a full synthetic **mouse** traversal does. And jsdom measures nothing, so XYFlow never draws a `.react-flow__edge` element under jsdom - the arrow is only assertable in a real browser. So: the model + pure mappings are unit-tested (`edges.test.ts`, `cross-apply.test.ts`, `flow-drag.test.ts`, `flow-edge.test.ts`, node-host draggable case); `cross-apply-flow-sheet.test.tsx` proves the *panel* renders both contentions after a cross-application and records the edge in the doc (not the edge DOM); the actual drag→copy→transparent-arrow→persist path was verified in Chrome via a synthetic mouse-drag traversal. **`crossApplyContention` in a Yjs `toString()` shows `<argument>`/`<response>` node names, not the ProseMirror `data-flow-*` render attributes** (those are added by `renderHTML`, never stored).

### Strike-on-drop (`src/flow/strike.ts` + adjacency in `flow-drag.ts` + `ContentionNode`)

Slice 2/3 of the **DnD/Strike** PRD: dropping a dragged argument (a contention) **adjacent** to an opponent's argument applies a non-destructive **strike-through** to that opponent argument - the clash move where answering an argument crosses it out. It composes with slice 1: a drop next to an opponent argument **both cross-applies AND strikes** (copy + arrow + strike, per the PRD's clash workflow). Strike model re-exported from `src/flow`; the adjacency geometry from `src/flow/canvas`.

- **Strike is a flag *on the node*, not a new fragment (`strike.ts`).** A strike is a property of one node (unlike an edge, which relates two), so it is a `struck` boolean field (`STRIKE_FIELD`) on that node's nested `Y.Map` in the existing `nodes` fragment - read via the public `FLOW_NODES_FRAGMENT` constant so strike stays orthogonal to and never re-implements the node store. This buys two things free: **no orphans** (`removeNode` deletes the whole node map, so a struck node's flag goes with it - no cascade cleanup like edges need), and **live rendering** (`observeNodes` observes the `nodes` map *deeply*, so setting/clearing the flag fires the same observer the label already uses). The flag is orthogonal to the content-free `FlowNode` snapshot - `struck` never appears in it. Seam: `isNodeStruck`/`setNodeStruck`/`toggleNodeStruck` (all no-op/`false` on a missing node, never throw). **Only the struck state is stored** (clearing *deletes* the field, mirroring the "only overrides stored" discipline), so an unstruck node persists nothing and the default is always unstruck; being a field on the persisted `nodes` map, a strike survives reload exactly like membership. **Gotcha - `toggleNodeStruck` re-reads after the set** so a no-op on a missing node reports the true (unstruck) state, not the intended flip.
- **Adjacency is explicit vertical geometry (`resolveAdjacentNode` in `flow-drag.ts`).** The pure sibling of `resolveNodeDropColumn`: given the drop's vertical center and the target column's laid-out node slots (`DropTargetNode` = `{ id, y, height }`), it returns the id of the node the drop landed *next to*, or `null`. Definition: for each candidate, the gap between `centerY` and its slot `[y, y+height)` (0 when *inside*); the **nearest** node wins, but only if that gap is within `ADJACENCY_MARGIN` (= `FLOW_NODE_GAP`) - so a drop on an argument or in the immediate whitespace beside it strikes it, while a drop in far-off empty column space (or an empty column) strikes nothing. All coordinates are column-relative and every column sits at canvas y-origin 0, so the dragged node's `position.y` is directly comparable to a target node's `y`.
- **The canvas resolves both, the panel applies both.** `FlowCanvas.onNodeDragStop` now computes the adjacent target node (filtering `flowNodes` to the target column for their `position.y`/`height`) and passes it as a **4th arg** to `onNodeCrossColumnDrop?(nodeId, from, to, adjacentNodeId)`. `FlowSheetPanel`'s handler runs both `crossApplyContention(...)` and, when `adjacentNodeId` is non-null, `setNodeStruck(handle, adjacentNodeId, true)` inside **one `handle.doc.transact()`** - copy + strike is one atomic Yjs step. The canvas stays a pure view - it computes geometry and delegates the mutation.
- **Rendering: clear, non-destructive, clearable (`ContentionNode`).** A struck contention carries `data-struck="true"` and a `line-through decoration-2 opacity-70` treatment - the argument's text stays **readable** (line-through, not removed; label + body still render). A small **✕ clear-strike button** (`data-testid="contention-clear-strike"`, `no-underline`) appears absolutely-positioned top-right **only while struck and not collapsed** (an unstruck contention carries no strike chrome; a collapsed one hides it too since the body is not visible) and calls `setNodeStruck(..., false)` - the discoverable "re-toggle" clear path. Strike state is read via `useNodeStruck`, a hook that rides `observeNodes` (the flag lives on the node map) so the node restyles live.
- **Testing reality mirrors slice 1 - the real drag→strike gesture needs a browser.** The model is unit-tested (`strike.test.ts`: defaults, set/clear, toggle, no-disturb-membership, missing-node no-op, forget-on-remove, close/reopen persistence), the adjacency geometry purely (`flow-drag.test.ts` `resolveAdjacentNode` cases: inside-slot, immediate-gap-nearest, beyond-margin→null, empty), the rendering + clear control (`ContentionNode.test.tsx`), and the composed clash *result* through the real panel (`strike-flow-sheet.test.tsx`: opponent struck + copy present + arrow recorded, only the opponent struck). The actual synthetic **mouse**-drag-drop-adjacent→**cross-apply + strike + persist** path was verified in Chrome (drag aff contention onto the neg contention's slot → opponent gets `data-struck`, a neg copy + arrow appear, strike survives a fresh document open, and the ✕ button clears it).

### The copy / arrow / strike model, end to end (slice 3/3) + closeout e2e

The **DnD/Strike** PRD is complete. The clash model the speech-doc pipeline PRDs consume next is a short pointer:

- **Cross-application = copy + arrow, one atomic step.** `crossApplyContention(handle, nodeId, targetColumnId)` (`src/flow/cross-apply.ts`, re-exported from `src/flow`) mints a fresh contention in the target column, deep-clones the source's argument-row content (and nested subpoints) into the copy's id-derived fragment, and records a `CROSS_APPLICATION_EDGE_KIND` arrow original→copy in the `edges` `Y.Map` (`src/flow/edges.ts`) - all in one `doc.transact`. The original stays put; the copy is a true independent copy that then diverges. Edges are a sibling fragment of `nodes`/`subpoints`, cascade-deleted with a node (`removeEdgesForNode` inside `removeNode`) so no orphans accumulate.
- **Strike = a non-destructive `struck` flag on the node** (`src/flow/strike.ts`), a field on the node's own `Y.Map` in the `nodes` fragment - `setNodeStruck`/`isNodeStruck`/`toggleNodeStruck`. Only the struck state is stored; it rides `observeNodes` for live rendering and persists with membership.
- **The clash gesture (drop adjacent to an opponent argument) = cross-apply AND strike in one `handle.doc.transact()`** - exactly what `FlowSheetPanel.onNodeCrossColumnDrop` runs after the canvas resolves the drop geometry (`resolveNodeDropColumn` picks the target column, `resolveAdjacentNode` picks the opponent node). **One drag gesture is one Yjs transaction, hence one undo step** - a `UndoManager` scoped to the `nodes` + `edges` stores collapses the whole clash into a single stack item that one `undo()` fully reverts (copy gone, arrow gone, strike cleared; the copy's orphaned content fragment stays but is invisible without its node - the graceful-orphan discipline). Copies, arrows, and strikes all persist across a reload.
- **Closeout e2e:** `dnd-strike.e2e.test.tsx` composes the whole stack the way `FlowSheetPanel` ships it (round seam → real per-node Tiptap text → the canvas's own pure drop geometry → the one-transact cross-apply + strike), then proves the single-undo-step property (via a `UndoManager` over `FLOW_NODES_FRAGMENT` + `FLOW_EDGES_FRAGMENT`) and that copy + cloned text + arrow + strike all survive a fresh-instance service reload. Follows the `argument-rows-collapse.e2e` / `contention-subpoint.e2e` / `flow-sheet.e2e` closeout precedent. **jsdom gotcha:** XYFlow's d3-drag needs real DOM measurement, so the e2e drives the pure geometry + model mutation the handler runs (not the pointer gesture, which is browser-verified); it authors/reads argument text through a genuine editor over the same fragment the panel binds to (`migrateFlowNodeFragment` + `FLOW_ARGUMENT_PRESET`), since jsdom cannot type through the rendered panel editor.

## Floating timer widget (`src/timer/`)

The floating Timer widget overlaid on the flow sheet (PRD: Flow Sheet Widgets): two side-coloured prep timers, a dynamic speech timer, all click-to-edit.
It is deliberately **self-contained** - it depends only on the app shell (design tokens) and holds no document/Yjs/IPC coupling; every timer is **component/session state only, nothing persisted** (persisting timer history is explicitly out of scope). Re-exported from `src/timer`.

- **`useCountdown(initialSeconds)` is the shared engine** behind every timer: `{ seconds, running, start, pause, toggle, reset, setSeconds }`. It ticks off a single `setInterval` that exists only while running (a paused timer holds no timer resource), clamps at 0 (auto-pausing there via a pure effect, never counting negative), and `reset` restores `initialSeconds` while `setSeconds` (the click-to-edit commit) changes the live time *without* moving that reset baseline.
- **Gotcha - never nest a state setter inside another setter's updater.** React StrictMode (on in `main.tsx`) double-invokes state updaters in dev, so a `setRunning(...)` called inside a `setSecondsState((s) => {...})` updater fires **twice** and cancels itself out - `toggle`/`start` silently no-op in the real app while unit tests (no StrictMode) still pass. The guard-against-a-spent-clock read that tempted the nesting instead rides a `secondsRef` (kept current each render) so `start`/`toggle` read the latest seconds with a **pure** `setRunning` updater. `useCountdown.test.tsx` has a `renderHook(..., { wrapper: StrictMode })` regression test pinning this; this bug is invisible to non-StrictMode tests, so **browser-verify timer controls** (this was caught via chrome-devtools-axi, not the suite).
- **`formatTime`/`parseTime` (`countdown.ts`, pure)** are the `M:SS` display/parse contract click-to-edit rides; `parseTime` is the inverse of `formatTime` for any value it produces (accepts `M:SS`/`MM:SS` with 0-59 seconds, or bare seconds; returns `null` on unparseable input so the editor keeps the prior value). `DEFAULT_PREP_SECONDS = 180` (the PRD's 3:00); `DEFAULT_SPEECH_SECONDS = 300` is an arbitrary editable starting point (speech lengths vary by format).
- **`EditableTime`** renders the formatted time as a `<button>`; a click swaps it for a text field seeded with the same string. Enter/blur commits via `parseTime`; Escape or an unparseable value discards. Editing is local UI state - it never pauses/resumes the countdown. **aria-label gotcha:** the editable value's label (e.g. `"Aff prep time"`) is a substring of the control labels (`"Play Aff prep timer"`), so tests must query the value button with an **exact** name, not a `/regex/` (a regex matches the play/pause/reset buttons too).
- **`PrepTimer`** (`side: "aff" | "neg"`, a local `TimerSide` type to stay self-contained) is a 3:00 countdown coloured by the aff/neg design tokens (`border-*-strong`, `text-*-strong`, `bg-*-soft`) with play/pause + reset; the section carries `data-side`. **`SpeechTimer`** is one editable countdown whose label is the selected speech: a selector row of `SPEECH_OPTIONS` (`AC`, `NC`, `CX`, `AR`) plus a `>` advance button (wraps past the last back to the first). **Selecting or advancing only relabels the running speech - it never touches the countdown**, so switching speeches never interrupts timing (or flowing).
- **`TimerWidget`** composes both prep timers + the speech timer inside a `pointer-events-none absolute inset-0` overlay whose card is `pointer-events-auto` - so clicks anywhere outside the card **pass straight through to the flow beneath**, satisfying the PRD's "floats over the flow without blocking flow interactions".
  - **Placement - overlay the canvas, not the whole panel.** `RoundScreen` hands the widget to `FlowSheetPanel`'s optional `overlay` slot (`<FlowSheetPanel handle={...} overlay={<TimerWidget />} />`), which renders it inside the **canvas** wrapper (made `relative`) - above the flow columns but **clear of the column-controls strip above and the RFD region below**. It is *not* a sibling of the panel: mounting it over the whole panel pinned it top-right where it fully covered the "Add column" button on a fresh (column-less) round, making the first action unclickable. Keep the timer in the `overlay` slot so it only ever floats over the flow columns.
- **Tests:** `countdown.test.ts` (pure format/parse + inverse), `useCountdown.test.tsx` (tick/play/pause/reset/edit/clamp + the StrictMode regression, `vi.useFakeTimers`), `EditableTime.test.tsx` (commit-on-Enter/blur, discard-on-Escape/unparseable), `PrepTimer.test.tsx` + `SpeechTimer.test.tsx` (default 3:00/5:00, play/reset, edit, side colouring, selector switching + advance-wrap, switch-doesn't-disturb-countdown), `TimerWidget.test.tsx` (composition + pass-through overlay class hooks).

### Split-screen docking (`src/speech-doc/dock/`)

## Send Flow -> Speech Doc pipeline (`src/flow/send-to-speech.ts` + `src/flow/canvas/`)

The **Send Flow** PRD: a debater Shift+Click multi-selects flow arguments (contentions and/or subpoints) and presses **Ctrl/Cmd+Enter** to append their content onto the end of the {@link ../speech-doc/active-speech-doc | active speech doc}, non-destructively. It reuses the active-speech-doc contract (PR #83) as the target and touches neither the argument-row transitions nor shorthand expansion. Model re-exported from `src/flow`; the selection/gesture/control from `src/flow/canvas`.

- **The append core (`send-to-speech.ts`, model-layer, Yjs-level).** `appendFlowNodesToSpeechDoc(flowHandle, speechHandle, nodeIds, bodyFragmentName?)` reads each selected container's own content fragment (`contention:<id>` / `subpoint:<id>`), **deep-clones every non-empty `<paragraph>` element** (Yjs `clone()`, mark-preserving + doc-agnostic, exactly like the cross-apply copy), and pushes the clones onto the speech doc body fragment (`SPEECH_DOC_BODY_FRAGMENT`) in **one transaction**. Append order is the flow's own reading order (columns, then contentions top-to-bottom, then their subpoints), regardless of selection order; ids that no longer resolve are skipped. Returns `{ nodeCount, paragraphCount }`. **Why flatten to paragraphs:** a flow box stores `argument > response > paragraph` but a speech body is plain `block+` with no `argument`/`response` node types, so only the shared `paragraph` type is extracted. Rich Auto-Speech reshaping is a **separate PRD, deliberately out of scope** - this is a faithful append. **It works at the Yjs level (not via an editor) on purpose:** collapsed containers mount no editor, so the pipeline must read fragments directly. **Non-destructive by construction:** the flow side is read-only; every write lands in the speech doc's own `Y.Doc`, so it persists + reloads like any speech-doc edit. **Gotcha - building detached Yjs XML:** use `applyDelta` + `insert` (never `.push` or attributed `.insert` on an *unintegrated* `Y.XmlText`/`Y.XmlElement`), else Yjs logs `Invalid access: Add Yjs type to a document before reading data` (the `.push`/format path reads `.length`/`.doc`). The migrate helper and the send tests follow this.
- **The selection (`useFlowSelection.ts` + `FlowSheetContext.selection`).** A transient `FlowSelectionState` (`selectedNodeIds`/`count`/`isSelected`/`toggle`/`clear`) owned by `FlowSheetProvider`, alongside the active-column and collapse state - **never persisted** (a send gesture, not a case property; a reload starts empty, and it never enters the Yjs types). `ContentionNode` and `SubpointNode` toggle their own id on **Shift+Click**, handled on `onMouseDownCapture` (so it wins over XYFlow's drag-start and the editor's caret/text-selection) with the follow-up click swallowed on `onClickCapture` (so the header's collapse toggle never fires for the same gesture). Selected containers carry `data-selected` and a `ring-2` treatment (dark ring on contentions, light ring on the dark subpoints). Shift+Click again deselects.
- **The gesture + affordance (`SendToSpeechControl.tsx`).** In the panel's toolbar strip beside the collapse button: a **Send to speech (N)** button (enabled once selection is non-empty) plus the document-wide **Ctrl/Cmd+Enter** hotkey - both call the same send. The hotkey deliberately uses **Ctrl/Cmd+Enter, never plain Enter/Shift+Enter**, so it never collides with the argument-row transitions or shorthand expansion those keys drive; it only acts on a non-empty selection (else it passes through) and `preventDefault`s when it acts. On success it clears the selection and shows a `role="status" aria-live` line ("Sent N argument(s) to your speech.").
- **No-active-doc = deliberate reversible no-op (tested).** When no speech doc is active, sending mutates nothing and surfaces a subtle inline affordance ("No active speech doc - open or select a speech to send into.") with the **selection preserved** so the debater can pick a target (via the dock's active-speech `<select>`) and retry. Auto-creating a doc from a chord was rejected: it would spawn stray docs and silently choose a target. **Provider-tolerance:** the control reads the `DocumentService` via a local `useOptionalDocumentService` (reads `DocumentsContext` directly -> `null` outside a provider, like the dashboard resume reader) and the active id via the provider-tolerant `useActiveSpeechDoc`, so the bare-`FlowSheetPanel` canvas tests (no `DocumentsProvider`) still render. It opens the target through `service.open(activeId)` (the service's cached handle - the same one the dock may already have open).
- **Tests:** `send-to-speech.test.ts` (`fake-indexeddb`, real flow + speech handles) is the highest seam - multi-select appended in flow order, selection filtering, nested subpoints, **mark preservation**, **flow untouched**, **persist across a speech-doc close/reopen**, multi-paragraph/empty-skip, and the empty/no-text no-ops. `useFlowSelection.test.tsx` covers toggle/deselect/multi-select/clear/stable-snapshot. `SendToSpeechControl.test.tsx` (real `DocumentsProvider` + `ActiveSpeechDocProvider`) covers disabled-until-selected, send-on-click + selection-clears + flow-intact, the Ctrl/Cmd+Enter hotkey, and the no-active affordance with preserved selection. The real Shift+Click / XYFlow gesture + Cmd+Enter send was **browser-verified in Chrome** (jsdom can't drive XYFlow), including the no-active affordance and the append landing in the dock's active speech.

## Drag a card into the Speech Doc (`src/speech-doc/card-drag.ts` + `card-drop.ts` + `card-drag-transfer.ts`)

The **Speech Doc Card Pipelines** PRD (drag track): a debater drags an individual block-file card by its grip **directly into the docked speech doc**, and it lands - COPIED, Auto-Speech-formatted, *with its argument-section heading* - at the precise drop position (not a bottom-append). It reuses the {@link ../speech.transformToSpeech | Auto Speech engine} and the {@link ./active-speech-doc | active-speech-doc contract} (PR #83); the block file is never mutated. All three modules re-exported from `src/speech-doc`. (Distinct from the **Send Flow** pipeline above, which appends *flow* content; and from the parallel ToC bulk-send track.)

- **Why the pipeline lives in `src/speech-doc`, not `src/blockfile`.** The drag source consumes both the block-file card APIs *and* the speech engine; the block file is the lower-level module and must not depend on speech. So both halves sit in `speech-doc` (which already depends on `blockfile` + `speech`) - **no dependency cycle**, and `blockfile/index` stays speech-free. `BlockFileScreen` (a top-level screen, free to compose features) imports the drag extension from `src/speech-doc/card-drag`.
- **The wire format (`card-drag-transfer.ts`) is a tiny, dependency-free seam.** It owns only the custom MIME `CARD_SPEECH_DRAG_MIME = "application/x-fulcrum-card-speech"` and `writeCardSpeechBlocks`/`readCardSpeechBlocks`/`hasCardSpeechDrag` over a `DataTransfer`. Both halves import it *without importing each other*. **The engine runs on the DRAG side** (which has the card node types) and the speech-ready block-level document-JSON travels on the drag - so the drop side is fully schema-agnostic (it inserts plain paragraph/heading/text+bold JSON, all present in the speech-doc preset). `hasCardSpeechDrag` reads `DataTransfer.types` (not `getData`, which browsers blank during `dragover`) so the drop target can decide to accept during `dragover`.
- **Drag source (`card-drag.ts`, `CardSpeechDrag` extension on the block-file editor).** A ProseMirror plugin renders a per-card **drag handle** as a view-only **widget decoration** at `cardPos+1` (a `⠿` grip, `draggable`, `contenteditable=false`) - no schema/document change. The handle's own `dragstart` listener (closed over `getPos`, so it reads the card's *live* position) calls `buildCardSpeechDragData(doc, pos, options?)` and writes the result, then `stopPropagation()`s so ProseMirror's internal node-drag never overwrites the payload (this is a pure external HTML5 drag). `buildCardSpeechDragData` is **pure** (reads the doc only): it `cardAt`-locates the card, finds the enclosing argument-section heading (nearest preceding level-`BLOCK_SECTION_HEADING_LEVEL` heading **scoped to the card's own side**, so a neg card never picks up an aff heading), wraps `[heading?, card]` under a throwaway `doc.type.create(null, ...)` (the `create`-not-`createChecked` pattern the Auto Speech clipboard tool uses), and runs `transformToSpeech`. Returns `null` for a non-card pos or an empty card (→ the drag carries nothing). CSS (`src/index.css`): `[data-card]` is `position:relative` and the handle is absolutely placed just left of the card, revealed on hover.
- **Drop target (`card-drop.ts`, `SpeechCardDrop` extension on the speech-doc editor).** A plugin whose `handleDOMEvents` (`dragover`/`dragleave`/`dragend`/`drop`) act **only** on a card-speech drag (else return `false`, leaving normal handling untouched). `dragover` `preventDefault`s + sets `dropEffect="copy"` (the copy cursor) and moves a live **drop indicator** (a horizontal-line widget decoration) to the resolved boundary, plus an `is-card-drop-target` class on the editable (CSS highlight + `cursor:copy`). `drop` inserts the payload's blocks. **Precise placement = resolve then snap:** `resolveSpeechDropPos(view, coords)` = `view.posAtCoords` then `snapDropPos(doc, pos)` - a **pure** function rounding to the nearest top-level block boundary (before the block if the pointer is in its top half, after otherwise), so block content never splits a paragraph. `insertSpeechBlocksAt(view, blocks, rawPos)` snaps again (idempotent) and inserts, returning the range.
- **Co-location: `BlockFileScreen` docks the speech editor** (wraps its editor column in `SpeechDockLayout`) so the card (drag source) and the active speech doc (drop target) are on one screen. **Gotcha this surfaced:** the dock adds a *second* `list()` consumer to the screen, so `blockfile-workspace/workspace.test.tsx`'s "retries and recovers" test could no longer key its transient failure to a `list()` **call count** (effects run child-first, so the dock's `useSpeechDocs` reads the registry *before* `useBlockFile`) - it now fails every `list` until a `recovered` flag is flipped before the retry click. `SpeechDocEditor` gained the `SpeechCardDrop` extension via a module-level `SPEECH_DOC_PRESET` (stable ref per the `useDocumentEditor` contract), so the drop works wherever the editor mounts (the dock *and* the standalone `/speeches/:id` route).
- **Testing reality (mirrors the flow-DnD precedent - real DnD needs a browser).** The model + pure logic are unit-tested: `card-drag.test.ts` (payload incl. heading + bold tagline + highlighted-only body, non-card/empty → null, **side-scoped heading**, **doc unmutated**, handle rendering, the wire-format round-trip); `card-drop.test.ts` (`snapDropPos` before/after/clamp, `insertSpeechBlocksAt` **observable placement between existing blocks**, `handleSpeechCardDrop` with a **stubbed `view.posAtCoords`** proving the card lands at the resolved position, non-card drag ignored, the `dragover` indicator/`dropEffect`); `card-drag-drop.integration.test.tsx` composes both halves through a shared fake `DataTransfer` and asserts the Auto-Speech copy lands at the drop position **and the source block file is byte-for-byte unchanged**. **jsdom ships no `DataTransfer`** - tests use a tiny stand-in exposing `types`/`get/setData`. The real drag→drop gesture (grip drag, copy cursor, drop indicator, bold tagline landing in the docked speech, source card intact) was **browser-verified in Chrome** via scripted `DragEvent`s carrying a real `DataTransfer`.

## Block file (`src/blockfile/`)

The aff/neg side division is enforced by the ProseMirror schema - `doc` content is exactly `"affSection negSection"`.
Both section nodes are `isolating`, so a selection or edit cannot cross the boundary.

Install the schema via the feature-extension seam:
```ts
createEditor({
  binding: { handle, fragment: BLOCK_FILE_FRAGMENT },
  extensions: editorPreset({ extensions: blockFileExtensions }),
});
```

**Gotcha:** Tiptap logs `[tiptap warn] Duplicate extension names: ['doc']` because `blockDocument` overrides the baseline - this is expected and harmless.

The workspace singleton (`src/blockfile-workspace/`) is the first `block-file` document in the registry, found-or-created by `ensureBlockFile(service)`. The block-file screen (`src/screens/BlockFileScreen.tsx`) owns the editor via `useDocumentEditor` and passes it to `BlockFileTocPanel` - it does not use `DocumentEditor` directly (ToC needs the raw editor instance).

### Card node model (`src/blockfile/card.ts`)

A debate *card* is first-class structured content that lives inside a side region, not free-form prose.
`cardExtensions` (the `card` container plus its four region nodes) layers onto a block-file editor through the same shared-preset feature-extension seam as the side schema - append it after `blockFileExtensions`, together with `cardCreate` for the keyboard shortcut: `editorPreset({ extensions: [...blockFileExtensions, ...cardExtensions, cardCreate] })`.

- **One container, four fixed regions.** `card` (node name `card`, the only card node in the `block` group) has content expression `"cardTag cardTagline cardCite cardBody"` - one of each, in order, enforced by the schema exactly like the side division. The four region nodes are deliberately **out of every group** (reachable only by name from the card's content expression), so they can never appear on their own in a section and can never nest.
- **Region content rules.** `cardTag` / `cardTagline` / `cardCite` are `content: "text*"` with `marks: ""` - plain, single-line text with no marks (`text*` is what makes them single-line). `cardBody` is `content: "paragraph+"` - block prose whose text runs carry the shared marks; **bold and highlight apply here, independently and simultaneously on the same run**. `paragraph+` (not `block+`) keeps cards from nesting and keeps headings out of a card body.
- **The tag renders bracketed, stores bare - brackets are CSS, not DOM text.** `cardTag` accepts any free-form token (it is **not** a fixed enum - `[T]`, `[NU]`, `[CP]`, ...); the token is stored without brackets and `cardTag` renders a single content hole (`["span",{"data-card-region":"tag"},0]`, like the tagline/cite regions). The enclosing `[` `]` are **CSS `::before`/`::after`** on `.block-file-editor [data-card-region="tag"]` in `src/index.css`. **Gotcha (data-loss regression, fixed) - never render decorative chrome as a DOM text node beside a region's contentDOM.** The tag originally rendered literal `[`/`]` text nodes flanking an inner `data-card-tag-token` span; those sibling text nodes broke ProseMirror's input reconciliation for the region, so typed characters landed in the contentEditable DOM but never became a transaction - the tag silently accepted nothing and lost the text on reload. jsdom can't type into contentEditable, so `card.e2e.test.ts` (which seeds regions programmatically) never caught it; it only reproduces with real keyboard input in a browser. Keep any purely-visual affordance on a `text*` region in CSS (like the side-region labels), never in `renderHTML`.
- **Minimal CSS, data-attribute hooks.** Each region serializes with `data-card-region="tag|tagline|cite|body"`; the block file ships only the small `[data-card-region="tag"]` bracket pseudo-elements (above) and heading typography, scoped to `.block-file-editor`. Card region *formatting* (family/size/colour/weight) is driven separately by the formatting profile stylesheet (`src/formatting`), not here.
- **`buildCardContent(fields?)`** is a pure document-JSON builder (the seam the quick-create UI/tests use) - every field free-form and optional; its output matches what the schema auto-fills for a bare card (empty text regions, an empty body paragraph via `createAndFill`).
- **Gotcha - inserting a card via `insertContentAt`:** tiptap's `insertContentAt` *validates* content strictly (it does not `createAndFill` the inserted node), so insert a full node from `buildCardContent`, not a bare `{ type: "card" }`. Pass `{ updateSelection: false }` when inserting so the cursor is not placed inside the block-level card. Separately, y-prosemirror emits a one-time `TextSelection endpoint not pointing into a node with inline content (card)` warning if a *reloaded* document **begins** with a card (a non-textblock leading node); tests append cards after the side's leading paragraph to avoid the artificial edge.
- **This slice is schema/model + tests only.** Card-cutting tools come later. `card.test.ts` covers the four-region structure, `createAndFill` auto-fill, the card inside a side region, the free-form tag stored bare (no literal brackets in the serialized document), independent+simultaneous body marks, and a full Yjs round-trip (structure + marks).

### Card-as-a-unit addressability API (`src/blockfile/card-unit.ts`)

The pure query/selection seam that treats a card as an addressable **unit** on top of the card node model - the contract the card-cutting tools (Extract, Send to Block File) and drag-to-speech pipeline target. Re-exported from `src/blockfile`. Like `sideRegionsFromDoc`/`getSideSections`/`buildOutlineTree`, it is a pure derivation of ProseMirror state (no UI, nothing to invalidate); it splits into positional **location** and pure **content reading**.

- **Location.** `cardAt(doc, pos)` is the pure doc-node locator: it resolves `pos` to the enclosing `card` via ancestor walk and returns a `LocatedCard` (`{ node, from, to, regions }`) or `null`; `getCardAt(editor, pos)` is the editor form. `from`/`to` bound the whole card node - `from` is the position immediately before it (the `NodeSelection` anchor), so `[from, to]` is the range a cutting tool replaces/slices. `regions` is a `Record<CardRegionKey, LocatedCardRegion>` (keys `"tag"|"tagline"|"cite"|"body"`, ordered in `CARD_REGION_KEYS`); each region carries its node and its own `from`/`to` (content sits at `[from+1, to-1]`). **Snapshot discipline:** every position is valid only against the document version it was read from - re-derive after edits, same as the outline/side-region/section queries.
  - **Gotcha - out-of-range yields `null`, never throws:** `cardAt` guards a non-integer or out-of-`[0, doc.content.size]` `pos` and returns `null`, so a raw selection position can be passed without pre-validation (unlike `sideRegionsFromDoc`, which throws on a malformed doc).
- **Selection.** `selectCard(editor, pos?)` sets a `NodeSelection` on the whole card (`pos` defaults to the card enclosing the current selection), returning `true`/`false` (no-op) on hit/miss. It sets the selection only - **it does not focus** - so it composes with a tool that immediately transforms the selection. `getSelectedCard(editor)` reads "the card I'm working in" off the current selection; it matches both a cursor inside a card *and* a `NodeSelection` on a card (the latter's anchor sits *before* the card, so ancestor resolution alone would miss it - it is handled explicitly).
- **Reading/serialization (pure over a card node, no positions).** `readCardRegionText(card, key)` = one region's flattened text; `serializeCardRegion(card, key)` = one region node's document-JSON (marks preserved - use this for the body, not text); `readCardRegions(card)` = a `CardRegionsSnapshot` (`{ tag, tagline, cite }` as text + `body` as JSON); `serializeCard(card)` = the whole card as one re-insertable JSON node (the Extract/Send payload). All throw a clear error if handed a non-`card` node.
- **Tests:** `card-unit.test.ts` drives the locator from positions found by an *independent* document walk (never the API under test), and covers: locate-from-body/header, null for preamble/out-of-range/non-integer positions, `cardAt` doc purity, keyed region exposure; `NodeSelection` spanning the whole card + returns-true, miss returns-false-and-no-op, default-to-current-selection, `getSelectedCard` under cursor/node-selection/preamble; per-region text + JSON reads, body-mark preservation through serialization, whole-card snapshot, re-insertable whole-card round-trip, and the non-card throw.

### Quick card creation (`src/blockfile/card-create.ts`)

The one-gesture "new card" command layered on the card node model - the fast, no-dialog affordance a debater uses to drop a fresh, schema-valid card skeleton and start typing immediately. Re-exported from `src/blockfile`.

- **Two seams, one code path.** `insertCard(editor, options?)` is the imperative command (the same plain `(editor, ...) => ...` shape as `section-ops`); the Block File screen's *New card* button and the keyboard shortcut both call it, so there is one creation path. `cardCreate` is a tiny `Extension` carrying **only** the keyboard binding - append it after `cardExtensions` in the shared preset's feature-extension seam (`editorPreset({ extensions: [...blockFileExtensions, ...cardExtensions, cardCreate] })`), which is exactly what `BlockFileScreen`'s preset now does. Without `cardExtensions` in the preset the card node types are not in the schema and creation cannot work - the screen previously shipped `blockFileExtensions` only.
- **`CARD_CREATE_SHORTCUT = "Mod-Shift-c"`** - a `Mod-` chord mirroring the shared marks' shortcut convention (`Mod-b`, `Mod-Shift-h`); `c` is the card mnemonic. The button is inherently keyboard-reachable too (a real `<button>`, Tab + Enter). `BlockFileScreen` renders a platform-aware tooltip (`⇧⌘C` on macOS, `Ctrl+Shift+C` elsewhere) but the binding stays `Mod-Shift-c`.
- **Follows the caret, works in both sides.** `cardInsertPos` reads that a block file is `doc(0) > side(1) > block(2) > ...`, so depth-1 is always the side section and depth-2 the caret's top-level side block; it inserts the card as the **next sibling after that block** (`$from.after(2)`), so the card appears where the debater is working and the side never *begins* with a card (dodging the y-prosemirror leading-node warning). Fallbacks append to a side's `contentEnd`: when a `side` option is forced, or when the caret is not resolvably inside a side (e.g. a fresh unfocused editor - defaults to aff).
- **Cursor lands in the tag, ready to type.** The card opens at the insert position `at`, so `at + 2` is the first text position inside the empty `cardTag` region; `insertCard` inserts with `{ updateSelection: false }` then `setTextSelection(at + 2)` + `focus()` in one chain (one undo step). The next keystroke fills the tag.
- **Tests:** `card-create.test.ts` (unit, `fake-indexeddb`) covers the four-region insert, caret-lands-in-tag (typing flows into the tag), aff-and-neg placement, the explicit-`side` override, field seeding, sibling-after-current-block placement, and the extension registration + shortcut constant. `screens/BlockFileScreen.test.tsx` drives the real routed screen: the *New card* button appears once the editor mounts and one click renders a full card (all four `data-card-region` hooks) in the document.

## Evidence formatting standards (`src/formatting/`)

The model + preferences wiring for the product's house evidence formatting standards (Evidence Formatting Standards & Customization feature). The core (`profile.ts`, `preferences.ts`) is pure - **no Tiptap, no React**; slice 2 adds a pure profile→CSS mapping (`css.ts`) and a small React rendering layer (`src/formatting/react/`). The Settings panel (`FormattingSettingsPanel.tsx`) is this feature's Settings screen contribution. Sibling slice still to land: the unformatted-shrink rule. Re-exported from `src/formatting` (the React layer is imported directly from `src/formatting/react` so the model index stays React-free).

- **The profile (`profile.ts`).** A `FormattingProfile` is `Record<FormattingTargetKey, FormattingEntry>`; a `FormattingEntry` is `{ fontFamily, fontSize, color, bold, underline }`. The five targets (`FORMATTING_TARGET_KEYS`, stable order) mix card anatomy with body mark state: `tag`/`cite`/`body` line up with the like-named card regions (the card's fourth region, `tagline`, is *not* a separately-standardised target here); `highlight` and `unformatted` are the two body **mark states** (highlighted read-aloud text vs. the small size un-highlighted text is shrunk to). `DEFAULT_FORMATTING_PROFILE` encodes the standards exactly: Tag Calibri 13pt Bold, Cite Calibri 8pt, Body Calibri 12pt, Highlighted Calibri 12pt Underlined, Unformatted Calibri 8pt (all `#000000`).
- **Size is a point string, consistent with the mark scale.** `fontSize` is a CSS point string (`"12pt"`), the exact representation the `src/editor/marks` font-size mark stores, so a rendered size drops straight onto the mark. On-scale sizes (8/12pt) are `FONT_SIZE_SCALE` members and `unformatted` is deliberately the scale **minimum** (the Shrink tool's target). Tag's `13pt` is an off-scale *fixed* size, so the field is a free point `string`, **not** the closed `FontSize` union - a legitimate off-scale standard must be expressible and every size stays user-editable.
- **The preferences section (`preferences.ts`).** `registerFormattingSection(store)` registers the profile as section id `"formatting"` (`FORMATTING_SECTION_ID`) and returns the typed handle; idempotent, so multiple slices may call it. The section's keys **are** the target keys and each value is the whole `FormattingEntry`, so `handle.getAll()` *is* a `FormattingProfile` (`readFormattingProfile(handle)` is the typed alias) - one object drives rendering, a `set` edits one target, `reset()` restores the whole standard. Fields are built with `satisfies Record<FormattingTargetKey, PreferenceField<FormattingEntry>>` so schema keys stay exact while each default holds at the widened `FormattingEntry` type (booleans widen - the store-core convention). Every field carries a `label` (from `FORMATTING_TARGET_LABELS`) so the Settings panel renders controls straight from the schema; `FONT_FAMILY_OPTIONS` is the font-control choice list (presentation metadata, not a constraint).
- **The Settings panel (`FormattingSettingsPanel.tsx` + `formattingSettings.ts`).** The feature's Settings screen contribution, wired into `SETTINGS_CONTRIBUTIONS` via `formattingSettingsContribution`. The panel renders one `<fieldset>` (role `group`, legend = `FORMATTING_TARGET_LABELS[key]`) per target, iterating `FORMATTING_TARGET_KEYS`, with **native inputs only** (no colour-picker library): font is a text input backed by a shared `<datalist>` of `FONT_FAMILY_OPTIONS` (suggestions, not a constraint - any family may be typed); size is a numeric point control that reads `parseFloat("12pt")` and writes back `` `${n}pt` `` (preserving the point-string contract); clearing the field and blurring restores the stored value - same blur-restore semantics as `SchemaSettingsPanel`'s numeric input; colour is `<input type="color">`; `bold`/`underline` are checkboxes. Each control edits **one field of one target's whole `FormattingEntry`** via `handle.set(key, { ...values[key], ...patch })`, so the one-object-drives-everything invariant holds and edits stay target-isolated. Reads ride `useSection(handle)`, so a change re-renders the panel and any other consumer live (open documents restyle without a restart); per-section reset comes from the Settings shell. **Gotcha - import from `../settings/types`, not the `../settings` barrel:** the barrel pulls `contributions.ts`, which imports `../formatting`, so going through the barrel from a formatting module is a runtime circular import (`defineSettingsContribution is not a function`).
- **Tests:** `profile.test.ts` pins the target keys, the per-entry shape, the exact standard defaults, and scale-consistency (unformatted === `FONT_SIZE_SCALE[0]`, on-scale defaults are scale members). `preferences.test.ts` (`fake-indexeddb`) covers registration under the well-known id, defaults == standards, per-field labels, idempotent re-registration preserving set values, per-entry editing isolation, reset-restores-standards, and a real `openPreferenceStore` round-trip (set survives restart, unset resolves to standard, reset forgets). `settings.test.tsx` renders the panel over a real registered section plus an independent `useSection` consumer to prove font/size/colour/bold edits apply live and stay target-isolated, the font datalist offers the shared families, blur-on-cleared-size restores the stored value, and `formattingSettingsContribution` surfaces a **Formatting** section (with panel) on the real `SettingsScreen`.

### Unformatted-text shrink rule (`src/formatting/shrink.ts`)

The standing rule that a text run matching **none** of the four named styles (`tag`/`cite`/`body`/`highlight`) is *unformatted* and adopts the profile's configured shrink size (default `unformatted` = 8pt). Split into a pure classification of editor state and a thin application command; re-exported from `src/formatting`. Slice 3/5 of the Evidence Formatting feature (sibling slices do live rendering of the *named* styles and the Settings panel - keep this scoped to the unformatted-run classification + shrink application).

- **Classification is pure, over structure + marks only, never over current size.** `classifyRuns(state)` walks the doc's text nodes in order and returns `ClassifiedRun[]` (`{ from, to, classification }`, adjacent same-class runs merged); `classifyRunAt(state, pos)` is the single-position convenience (null when no text sits there). A run resolves to a named style by its enclosing card region (`cardTag`→`tag`, `cardCite`→`cite`, `cardTagline`→`body` since the tagline inherits body styling) or by mark (a `cardBody` run carrying the **highlight** mark →`highlight`). Everything else is `UNFORMATTED_TARGET_KEY` (`"unformatted"`): an un-highlighted `cardBody` run (the common case) **and any loose prose outside a card**. Deciding the target from *meaning* (region/highlight), not from the size a run happens to carry, is deliberate - a size-based rule would be circular.
- **Region resolution is an ancestor walk**, mirroring the card-unit locator: for each text node it resolves the position and walks `$pos.node(depth)` outward for the nearest card-region node type. The header regions (`text*`, `marks: ""`) can never be highlighted, so they always map to their region's named style.
- **Application shares the font-size mark model.** `applyShrinkRule(editor, profile?)` sets every unformatted run to `shrinkSize(profile)` via the same addressable `textStyle`/`fontSize` mark `src/editor/marks` owns (so a shrunk run is queryable document data, and the size model stays consistent with the future Shrink tool). The configured size is written **verbatim** - a profile may standardise an off-scale shrink size; the closed `FONT_SIZE_SCALE` is the interactive Shrink tool's *stepping* scale (a later feature) and is intentionally not imposed here. It is idempotent (skips runs already at the size, restores the prior selection) and returns whether the doc changed. This slice is the standing default only - **not** the interactive Shrink tool's progressive cycling.
- **Tests:** `shrink.test.ts` (`fake-indexeddb`, real block-file+card editor) covers per-region classification, highlighted-vs-un-highlighted body runs, loose-prose-as-unformatted, ordered non-overlapping runs with exact positions, classify-is-a-pure-read, `classifyRunAt` hit + null, `shrinkSize` default/configured, and `applyShrinkRule` shrinking only unformatted runs (named styles untouched), honouring an off-scale configured size, idempotence, and the no-unformatted-runs→`false` case.

### Live card rendering (slice 2, `css.ts` + `src/formatting/react/`)

Renders card regions and highlighted runs to the active profile, updating live when the profile is edited. The card node model ships **no CSS**, only `data-card-region` hooks and the highlight `<mark>`; this slice is the "later styling PR" that keys off those hooks.

- **Pure mapping (`css.ts`).** `formattingProfileCss(profile, { scope? })` serializes a `FormattingProfile` to a scoped stylesheet string (the seam that makes "serialized styles match the profile" directly testable). Selectors: `tag`/`cite`/`body` → `[data-card-region="…"]`; `tagline` → styled **from the `body` entry** (no separate target - it inherits body); `highlight` → `mark`. Every rule is nested under `scope` (default `DEFAULT_FORMATTING_SCOPE = ".block-file-editor"`, the `EditorContent` wrapper class) so the standard never leaks onto unrelated UI.
- **Gotcha - region rules carry the full entry; the highlight-`<mark>` rule does not.** A region rule emits family/size/color/weight/decoration as the region's default (an inline `textStyle` font-size mark - e.g. one the Shrink tool applies - still wins over the stylesheet size, so region sizing is a default, never a fight). The `mark` rule emits **only** `font-family`, `color`, and the underline `text-decoration`; it deliberately **omits `font-size` and `font-weight`** because those axes are owned by the addressable font-size mark and the independent `bold` mark - a bold+highlighted run must stay bold, and a shrunk highlighted run must stay shrunk, so emitting them here would clobber those marks. (Consequence: `highlight.bold`/`highlight.fontSize` in the profile are not rendered by this rule; the underline is the highlight treatment that has no competing mark.)
- **Reactive layer (`src/formatting/react/`).** `useFormattingProfile()` reads the live merged profile off the shared preference store (registers the `formatting` section on first use - idempotent, so it composes with the Settings-panel slice) via the store's `useSection` seam, so any edit re-renders. It is **provider-tolerant** like the dashboard's resume reader: with no `PreferenceStoreProvider` it falls back to a private, never-mutated store and reports `DEFAULT_FORMATTING_PROFILE` (a bare subtree still renders correct cards, no throw). `CardFormattingStyles({ scope? })` reads that hook and renders a `<style data-card-formatting>` with the emitted CSS; `BlockFileScreen` mounts one inside its section, so editing a target rewrites the `<style>` in place with no editor remount/reload.
- **Tests:** `css.test.ts` (pure) pins the scoped selectors, the standard's per-region declarations (tag bold 13pt, cite 8pt, body 12pt), tagline-rides-body, the highlight underline, the deliberate `font-size`/`font-weight` exclusion on the mark rule, a customized-profile round-trip, and a custom scope. `react/react.test.tsx` covers the standard read, live re-render on edit, and no-provider fallback for both the hook and `CardFormattingStyles`. `screens/BlockFileScreen.test.tsx` drives the real routed screen: the standard renders as scoped card CSS, and editing the `body` target through the shared store updates the emitted CSS live (no reload).

## Card-cutting tool framework (`src/tools/`)

The registration contract every card-cutting tool (Extract, Shrink, Condense, Auto Speech - remaining later features) plugs into.
This is slice 1/4 of the Card-Cutting Toolbar & Tool Customization Framework and ships **the contract only** - no tool, no toolbar UI.
It is pure and React-free, following the documented-contract discipline of the card-unit API and the formatting profile.
Re-exported from `src/tools`.

- **A tool = `CardToolDefinition<S>`** (`registry.ts`): `{ id, label, description?, settings, applyToSelection }`. `settings` is a `SectionSchema` (the exact shape a `PreferenceStore` section registers - typed fields with defaults + render metadata, value type inferred from each `default`). `applyToSelection(editor, settings)` transforms the active Tiptap selection using the live `settings` snapshot and returns a boolean (the truthiness a command chain returns).
- **`createCardToolRegistry(store)`** returns a `CardToolRegistry` with `register(definition)` → `RegisteredCardTool<S>`, `get(id)`, and `list()` (registration order preserved via an insertion-ordered `Map`, so the future toolbar is stable). A `RegisteredCardTool` is `{ id, label, settings: SectionHandle<S>, apply(editor) }`; `apply` reads the tool's **live** settings off the store (`settings.getAll()`) and forwards them to `applyToSelection`, so a tool never runs with a stale copy.
- **Design choice - one preference section per tool, not a shared `tools` section.** A tool's settings register on the shared store (`src/preferences`) as their own section, exactly like the formatting feature. Rationale: the store's reset, subscription, and future Settings panel are all section-scoped, so a per-tool section gives "reset **this** tool to defaults" and "render **this** tool's panel" for free and keeps one tool's schema change from being a cross-tool concern. The section id is namespaced via `toolSectionId(id)` = `` `${TOOL_SECTION_ID_PREFIX}${id}` `` (`tool:<id>`) so a tool id can never collide with a non-tool section (`formatting`, ...); the section's `title` is the tool label.
- **Duplicate ids are idempotent-or-error, mirroring the store's own rule.** Re-registering the same id with the same label and a structurally-identical settings schema returns the existing registered tool (preserving already-set values - safe under StrictMode/hot-reload); a different label throws a tool-level error, and a different settings schema throws via the store's schema-equality check (it names the `tool:<id>` section). Empty id/label are rejected up front.
- **No `defineCardTool` helper needed** (unlike the Settings shell's `defineSettingsContribution`): `register<S>` infers `S` at the call site and the erased `RegisteredCardTool` from `list()` exposes only `apply(editor)` (no `S` in a parameter position), so there is no panel-style contravariance to launder.
- **Tests:** `registry.test.ts` (`fake-indexeddb`, real `openPreferenceStore` round-trip) covers register-returns-handle-with-declared-defaults, the namespaced section landing enumerably on the store with the label as title, registration-order `list`/`get`, empty id/label rejection, `apply` forwarding the editor + live settings snapshot (default → set → reset), idempotent re-register preserving set values, throw-on-different-schema and throw-on-different-label, a persistence round-trip (set survives restart, reset forgets), and an end-to-end test that builds a real Tiptap editor and proves `apply` inserts the tool's persisted setting at the genuine selection and re-reads it after an edit.

### Toolbar container on the editor surface (slice 2, `src/tools/react/` + `src/tools/demo/`)

The unified card-cutting toolbar mounted at the top of the block-file editor surface, built on the slice-1 registry. React layer imported directly from `src/tools/react` (like `src/formatting/react`) so the `src/tools` model index stays React-free; the demo tool lives in `src/tools/demo/`.

- **`CardToolbar({ editor, tools })`** (`CardToolbar.tsx`) is presentation only - it owns no tools and no settings. It renders a `role="toolbar"` labelled `Card tools`, one slot per `ToolbarTool` in `tools` (registration order). **It renders `null` when `tools` is empty**, so it never shows an empty bar. A tool with `renderControl` renders that control in its slot; a plain tool renders a `<button>` whose click calls `tool.apply(editor)` (the registry reads the live persisted settings and runs `applyToSelection`). `ToolbarTool` extends `RegisteredCardTool` with an optional `renderControl?: ({ editor, enabled }) => ReactNode`; the plain `RegisteredCardTool` the registry returns is a valid `ToolbarTool`.
- **Disabled = no applicable selection.** A card-cutting tool needs a card to act on, so *every* button is disabled (native `disabled` **and** `aria-disabled`) whenever there is no editor or `getSelectedCard(editor)` is `null`. Applicability is uniform across tools (they are all card-cutting tools) and is intentionally **not** a per-tool predicate on the registry contract - keeping this slice scoped to the toolbar UI, not the slice-1 contract.
- **Gotcha - the toolbar must self-subscribe to selection changes.** `useDocumentEditor` returns a *raw* editor that does **not** re-render React on transactions (unlike `@tiptap/react`'s `useEditor`). `CardToolbar`'s internal `useEditorTick` subscribes to the editor's `transaction` event and forces a re-render, so the enabled/disabled state tracks the live caret. Without it the toolbar would freeze at its mount-time state.
- **`useCardTools()`** (`useCardTools.ts`) builds a `createCardToolRegistry` over the shared `PreferenceStore`, registers the shipped tools (`SHIPPED_CARD_TOOLS`, memoised per store), and returns `ToolbarTool[]`. **Provider-tolerant** like `useFormattingProfile`: with no `PreferenceStoreProvider` it falls back to a private store so the toolbar still paints. `register` is idempotent, so re-renders never re-register or throw. `SHIPPED_CARD_TOOLS` spreads `CARD_TOOL_DEFINITIONS` (the real tools with settings) then appends the settings-less toolbar-only tools (`condenseTool`, `extractHighlightTool`) then the `demoCardTool` - so adding a real tool with settings to `CARD_TOOL_DEFINITIONS` is the only wiring needed. Tools that need a custom control (Send's destination picker, Auto Speech's async clipboard copy + confirmation) get `renderControl` attached here after registration; plain tools pass through unchanged.
- **`demoCardTool`** (`src/tools/demo/demoCardTool.ts`) is the reference tool that proves the seam end-to-end without shipping a real tool - the toolbar's counterpart to the `src/settings/demo` reference contribution, retired once real tools have fully replaced its coverage. It is **non-destructive**: `applyToSelection` calls `selectCard(editor)` (a `NodeSelection` on the enclosing card) and, per its one `focusAfter` boolean setting, focuses after. **Gotcha - a tool's settings schema must be a `type` alias, not an `interface`:** `SectionSchema = Record<string, PreferenceField<unknown>>`, and a TS `interface` lacks the implicit index signature needed to satisfy that constraint (a `type` alias to an object literal has it).
- **`BlockFileScreen` wiring:** the toolbar sits in a new `flex-col` editor column (right of the ToC, above the scroll region) via `const tools = useCardTools()` + `<CardToolbar editor={editor} tools={tools} />`, so it never crowds the sidebar or the document. The header's *New card* button is unchanged (card-*create*, not card-*cutting*).
- **Tests:** `CardToolbar.test.tsx` (real block-file+card editor, spy tools) covers button-per-tool in registration order, click-invokes-apply-with-editor+live-settings, disabled+aria-disabled with no card / no editor, enabled with a card, live disabled-state update when the caret moves into a card, and empty-tools→renders-null. `demoCardTool.test.ts` covers its id/label/settings, selects-the-card, and no-op-outside-a-card. `useCardTools.test.tsx` covers shipped-tools-with-a-provider (+ namespaced section on the store), no-provider fallback, and idempotent re-registration across re-renders. `screens/BlockFileScreen.test.tsx` proves the real screen renders the toolbar and enables a tool once a card is created.

### Per-tool enablement (`CardToolDefinition.isEnabled`)

The toolbar gates *every* tool on one baseline - a card is addressable at the selection (`getSelectedCard`) - but a tool can narrow that to its own precondition via the **optional** `isEnabled?(editor): boolean` on `CardToolDefinition` (a pure read of editor state, never a mutation).
The registry surfaces it as `RegisteredCardTool.isEnabled(editor)` (forwards to the definition's, defaulting to `true` when a tool declares none), and `CardToolbar` computes enablement **per button** as `cardSelected && tool.isEnabled(editor)` - so a tool with no predicate keeps the old uniform "enabled once a card is selected" behaviour, and one with a predicate (Condense) disables until its precondition holds.
This is why `BlockFileScreen.test.tsx` no longer asserts *every* toolbar button enables after a card is created - it checks the predicate-less `Select card` (demo) tool specifically.

### Condense tool (`src/tools/condense.ts`)

The first real card-cutting tool: collapses the multiple paragraphs a debater selects inside a card body into a single block of running text, preserving every inline mark (bold, highlight, `textStyle`/`fontSize`).
Registered into the toolbar via `SHIPPED_CARD_TOOLS` in `useCardTools` (id `condense`, label `Condense`); re-exported from `src/tools`.

- **Mechanism = join block boundaries, never rebuild content.** The command finds the selection's `$from.blockRange($to)` and `tr.join`s each paragraph boundary inside it, back-to-front (so earlier positions stay valid as the doc shrinks), each guarded by `canJoin`. Joining removes only the boundary and leaves the inline content - text nodes and their marks - untouched, which is exactly why marks survive losslessly (nothing is re-serialized or re-created).
- **Card boundaries are free.** `card` is `isolating`, so a text selection can never span out of one card body; the block range always resolves within a single card body and only that card's paragraphs merge. The single-line `text*` header regions hold no paragraph boundaries, so they are never touched.
- **Enablement.** `canCondenseSelection(editor)` (the shared read behind both the predicate and the command) is true only when the block range spans 2+ blocks; it is wired to `condenseTool.isEnabled`, so the toolbar button disables (on top of the card gate) until the selection spans multiple paragraphs. Running the command with a shorter selection is a no-op returning `false`. Condense has no user settings (empty `CondenseToolSettings` schema), so it is deliberately **not** added to `CARD_TOOL_DEFINITIONS` (which surfaces per-tool Settings panels) - only to the toolbar list.
- **Tests:** `condense.test.tsx` (real block-file + card editor, `fake-indexeddb`) covers N-paragraph merge into one block, mark preservation (bold/highlight/font-size), the single-paragraph no-op, `canCondenseSelection` true/false, card-boundary isolation (two cards, only the addressed one merges), the tool-definition shape, and the toolbar disabled/enabled/click integration. Positions come from an independent doc walk, never the command under test.

### Shrink tool (`src/tools/shrink/shrinkCardTool.ts`)

Progressively shrinks the **un-highlighted body text** of the card the caret is in, cycling a configurable point-size sequence and returning to normal at the end, so repeated clicks undo the shrink.
Re-exported from `src/tools`.

- **Split into pure `applyShrink(editor, sequence)` + the `shrinkCardTool` definition.** `applyShrink` acts on the card from `getSelectedCard` and reuses the formatting feature's `classifyRuns` + `UNFORMATTED_TARGET_KEY` (`src/formatting/shrink`) to pick the target runs, so Shrink and the standing shrink rule agree on "unformatted": only un-highlighted `cardBody` runs are targeted. Highlighted (spoken) runs classify as `highlight`, and tag/cite/tagline resolve to their own named styles, so all of those are **never** touched. Returns `false` (no-op) when the sequence is empty, the caret is not in a card, or the card has no un-highlighted run.
- **The cycle is font-size-mark based and off-scale-friendly.** Sizes are written as the same addressable `textStyle`/`fontSize` mark (`src/editor/marks`); "normal" is the *unset* state (no mark), so the last step clears the mark via `unsetFontSize` rather than writing a size. The default sequence steps **below** `FONT_SIZE_SCALE`'s minimum (`8pt, 7pt, 6pt, 5pt`), so Shrink deliberately does **not** go through the scale-guarded `setFontSize` helper (which throws off-scale) - it writes verbatim through the chain command, exactly as `applyShrinkRule` does. Cycle position is read from the leading target run's current size: unset/off-sequence restarts at step 0, the last step wraps to unset.
- **Sequence is the one configurable setting**, a comma-separated point-size string (`DEFAULT_SHRINK_SEQUENCE`), so it renders as a plain text control on the schema-generated Settings panel (`SchemaSettingsPanel`) and persists through the shared store. A bare number normalises to points (`"6"` → `"6pt"`).
- **Wiring - one app-level list drives both surfaces.** `shrinkCardTool` is added to `CARD_TOOL_DEFINITIONS` (`src/tools/cardTools.ts`), which surfaces its settings on the Settings screen **and** renders it in the toolbar: `useCardTools`'s `SHIPPED_CARD_TOOLS` spreads `CARD_TOOL_DEFINITIONS` (then `condenseTool`, then the `demoCardTool`), fulfilling the documented "adding a tool here wires it into both surfaces at once" contract - a future tool with settings needs only the one-line `CARD_TOOL_DEFINITIONS` addition. (Contrast Condense, which has no settings and is wired only to the toolbar list.)
- **Tests:** `shrinkCardTool.test.ts` (`fake-indexeddb`, real block-file+card editor) covers `parseShrinkSequence` (split/trim/drop-empty/normalise-bare-number), the definition's id/label/configurable-sequence setting, the full cycle down the sequence and back to normal (and restart), the highlighted run staying untouched across the whole cycle, tag/cite/tagline left unshrunk, the no-card no-op, and an end-to-end registry test proving a live-reconfigured sequence drives `apply` via `openPreferenceStore`.

### Highlight tool (`src/tools/highlight/` + `src/tools/react/HighlightStyles.tsx`)

The first real card-cutting tool, and the base the follow-up Extract Highlight slice queries.
`highlightCardTool` (`highlightCardTool.ts`) is a `CardToolDefinition`: `applyToSelection` is a plain `editor.chain().focus().toggleHighlight().run()` over the shared `HighlightMark`, so highlighted runs stay queryable by mark type and bold stays fully independent (separate ProseMirror marks - toggling one never touches the other).
It is wired into `CARD_TOOL_DEFINITIONS`, which `useCardTools` now spreads into the toolbar's shipped list (so a real tool is added in one place and reaches both the toolbar and the schema-generated Settings panel; the `demo` tool is a separate prepend, retired once real tools cover it).

- **Color is a live render preference, not a per-run mark attribute.** `HighlightMark` is `multicolor: false` by design (a boolean "read aloud" flag; the docblock forbids per-run colors without a schema-change PRD), so the configurable **color** is the tool's one setting (`color`, an enumerated `HIGHLIGHT_COLORS` palette - CSS keywords that double as labels, default `yellow`) applied globally via CSS, **not** baked into runs. `applyToSelection` therefore deliberately ignores `settings` (the mark is boolean). A color change reflects live on *every* highlighted run at once, including ones highlighted before the change.
- **`highlightColorCss(color, scope?)`** (pure) emits `<scope> mark { background-color: <color> }` - it sets **only `background-color`**, the one axis the formatting profile's `mark` rule leaves unclaimed (that rule owns the mark's text color, underline, and family), so the two stylesheets compose without a fight. It validates `color` against `HIGHLIGHT_COLORS` and falls back to `DEFAULT_HIGHLIGHT_COLOR` (`"yellow"`) for any unrecognized value, so the emitted CSS never interpolates an arbitrary string. Scope defaults to `HIGHLIGHT_TOOL_SCOPE` (`.block-file-editor`, matching the formatting scope).
- **`HighlightStyles`** (`src/tools/react/`, provider-tolerant like `useFormattingProfile`/`useCardTools`) reads the tool's live `color` off the shared store (registers the tool's section idempotently, rides `useSection`) and renders a `<style data-highlight-tool>`; `BlockFileScreen` mounts one beside `CardFormattingStyles`, so editing the color in Settings restyles the open document with no reload.
- **Tests:** `highlightCardTool.test.ts` (real block-file+card editor, positions from an independent doc walk) covers the id/label/color-palette schema, apply-adds-highlight, toggle-removes, bold independence, and the pure `highlightColorCss` (scoped background-color + custom scope). `react/HighlightStyles.test.tsx` covers the no-provider default and live update when the color changes on the store.

### Shared highlighted-runs query (`src/editor/marks/highlighted-runs.ts`)

The reusable primitive that answers "which runs carry the highlight mark", re-exported from `src/editor/marks`.
It is deliberately **not** private to any tool: **Extract Highlight** pulls a card's read-aloud runs, and the **Auto Speech** engine (`src/speech`) reuses the same function to assemble a speech from highlighted runs across many cards.
Pure and position-agnostic over ProseMirror structure + marks, the same discipline as `classifyRuns` and the card-unit API.

- **`highlightedRuns(node, basePos = 0)`** walks `node`'s text descendants and returns one `HighlightedRun` (`{ from, to, text, content }`) per *contiguous* stretch of highlighted text. Adjacent highlighted text nodes merge into one run (so a partly-bold highlighted span reads as one), while a paragraph boundary (which consumes a position) breaks contiguity into separate runs - so the caller can keep paragraph structure. `content` is the run's text node(s) as re-insertable document-JSON with **every** inline mark preserved (highlight, bold, `textStyle`/`fontSize`); `text` is that flattened. `from`/`to` are offset by `basePos`: pass `0` for offsets within the node, or the node's first inner position (`region.from + 1`) for absolute doc positions.
- **`hasHighlightedRuns(node)`** is the short-circuiting predicate a tool uses for enablement.
- Highlight detection is by mark type name (`HIGHLIGHT_MARK_NAME`), matching the merged Highlight tool's `toggleHighlight` - a boolean `multicolor: false` mark, so nothing depends on per-run color.

### Extract Highlight tool (`src/tools/extract/extractHighlightTool.ts`)

Isolates a card's read-aloud rhetoric: collects the highlighted runs of the card the caret is in and produces a fresh card containing only that content.
Re-exported from `src/tools`; wired into `SHIPPED_CARD_TOOLS` (toolbar-only, like Condense - it has no settings, so it is **not** in `CARD_TOOL_DEFINITIONS`, which surfaces per-tool Settings panels).

## Auto Speech transform engine (`src/speech/`)

The pure, framework-agnostic core of the Auto Speech PRD (slice 1/3): `transformToSpeech(node, options?)` turns card / selection content into speech-ready block-level document-JSON.
It is a deliberate **shared dependency** - the Auto Speech clipboard toolbar tool (slice 2), the ToC-checkbox speech pipeline, and the drag-to-speech pipeline all call it - so it is kept in the documented-contract discipline of the card-unit API and the highlighted-runs query: pure over a ProseMirror node, **no React, no toolbar coupling, no editor mutation**.
Re-exported from `src/speech`.

- **Input.** A ProseMirror `Node` (the currency of the card-anatomy APIs) - a whole block-file doc, a fragment of one, or a bare `card` node. The engine walks it in document order **without descending into a card** (a card node passed directly is transformed whole), collecting cards and section headers; loose prose *outside* a card is ignored (it is not read-aloud content).
- **Transform rules.** Per card: emit the **tag** (only if `includeTag`, default off - it is a tactical cutting label), the **tagline** rendered **bold** (a real `bold` mark, since card-region CSS does not reach a speech doc - the tagline carries no marks in a card, so the engine adds it), the **cite**, then the **body's highlighted runs flattened to plain text** (via the shared `highlightedRuns` query, all marks dropped), one output paragraph per source body paragraph that has highlights. **Un-highlighted body text is stripped entirely.** A **separator line** (`DEFAULT_SPEECH_SEPARATOR = "---"`) goes between adjacent cards; a section header between two cards is itself the divider, so no extra separator is added around it. **Section headers are preserved** as headings (level + text).
- **Output = `JSONContent[]`**, a flat list of block-level nodes (the speech body) a consumer drops onto a clipboard or into a speech document. No positions (the engine works structurally). An empty card (no enabled region has content) contributes nothing and does not trigger a separator.
- **Config (`SpeechTransformOptions`).** `separator` (string; `""` disables), `includeSectionHeaders`, `includeTag`, `includeTagline`, `boldTagline`, `includeCite` - so each downstream pipeline shapes output without forking the engine. Defaults encode the standard speech (bold tagline + cite + highlighted body, cards separated, headers preserved, tag omitted).
- **Tests.** `transform.test.ts` (`fake-indexeddb`, real block-file+card schema via `schema.nodeFromJSON`) covers the single-card rules (bold tagline, plain former-highlights, stripped un-highlighted, marks dropped, per-paragraph grouping), a bare card node, multi-card separators, header preservation + header-as-divider, every config variation, purity (input unmutated), and loose-prose-ignored. It builds docs directly from the schema rather than via editor commands since the engine is pure over a node.

### Auto Speech clipboard tool (slice 2/3, `src/tools/speech/`)

The card-cutting **Auto Speech** tool: runs the engine over the current selection and copies the speech to the clipboard. Model half re-exported from `src/tools`; the React control from `src/tools/react` (same split as Send).

- **Two clipboard flavours, always.** `writeSpeechToClipboard(payload)` writes `text/html` **and** `text/plain` at once via `ClipboardItem` (falling back to `navigator.clipboard.writeText` where `ClipboardItem` is unavailable), so a rich target (Word/Docs/speech doc) pastes the **bold tagline** while a plain target still gets readable text (one block per line). The HTML is produced by serializing the engine's `JSONContent[]` through the **editor's own schema** (`DOMSerializer.fromSchema(editor.schema).serializeFragment`), so `<strong>`/`<h2>`/`<p>` come out exactly as the editor renders them - this is why the block-file preset's `heading` + `bold` extensions must be in the schema (they are). Plain text = each block's `textContent` joined by newlines.
- **Selection → engine input (`speechSelectionNode`).** An empty caret uses the enclosing card (`getSelectedCard(editor).node`); a range collects the **whole** cards + section headers it intersects (`doc.nodesBetween`, `return false` on a card/heading so partial cards are never sliced) re-parented under `doc.type.create(null, Fragment.fromArray(items))`. **Gotcha:** use `create`, not `createChecked` - the block-file doc's content expression is `affSection negSection`, so a checked create of an arbitrary wrapper throws; `create` skips content validation and the engine only walks structure (never resolves positions against the wrapper), so it is safe.
- **Settings mirror the engine config, observed live.** `AutoSpeechToolSettings` is one `PreferenceField` per `SpeechTransformOptions` key (`separator`, `includeSectionHeaders`, `includeTag`, `includeTagline`, `boldTagline`, `includeCite`), so `SectionValues` **is** a valid options object and it renders straight from schema metadata on the `SchemaSettingsPanel` (booleans widened with `as boolean`). `autoSpeechTool` is in `CARD_TOOL_DEFINITIONS`, so it reaches both the toolbar and Settings; the registry passes its live snapshot on every `apply`, so a Settings edit is observed by the next copy.
- **Custom control for feedback (like Send).** An async clipboard write can fail and a silent copy is a poor affordance, so the toolbar presence is `AutoSpeechControl` (attached via `renderControl` in `useCardTools` for `AUTO_SPEECH_TOOL_ID`): a button that awaits `copySpeechToClipboard(editor, settings.getAll())` and announces the outcome in a `role="status"` `aria-live` line ("Copied speech to clipboard." / nothing-to-copy / failure). `autoSpeechTool.applyToSelection` is **not** a no-op (unlike Send): it performs a functional fire-and-forget copy with the live settings (honouring the registry contract + programmatic use), and the control adds the awaited feedback path on top.
- **Tests.** `auto-speech.test.ts` (`fake-indexeddb`, real block-file+card editor, stubbed clipboard) covers the tool-definition shape/defaults, `buildSpeechPayload` html+text (bold `<strong>` tagline, stripped un-highlighted, config observed, null-outside-a-card), `copySpeechToClipboard` writing both flavours, the `writeText` fallback, no-write-when-empty, and a registry round-trip proving live settings flow through `apply`. `AutoSpeechControl.test.tsx` covers disabled states, the copy + `aria-live` confirmation, and live-settings observation. **Test gotchas:** stubbing `navigator` must preserve `platform`/`userAgent` (Tiptap's `isiOS` reads them at editor creation, else `.includes` throws); jsdom's `Blob` has no `.text()`, so read blob content via `FileReader.readAsText`.

### Engine reuse contract (for the ToC-checkbox and drag-to-speech PRDs)

`transformToSpeech` (`src/speech`) is a deliberate **shared dependency**, not a private helper of the clipboard tool - two upcoming PRDs consume it directly and should call it rather than re-deriving speech shaping:

- **The ToC-checkbox "build a speech from the checked sections" pipeline** and **the drag-to-speech pipeline** both feed the engine a ProseMirror `Node` (a whole block-file doc, a fragment re-parented under a node, or a bare `card`) and drop its `JSONContent[]` output onto a clipboard or into a speech document. That is the same seam the clipboard tool uses via `speechSelectionNode` (`src/tools/speech/auto-speech.ts`) - reuse the "collect whole cards + headers, re-parent under `doc.type.create(null, …)`" pattern (`create`, never `createChecked`) when your input is a set of selected/checked nodes.
- The engine is pure over structure + marks (no React, no toolbar coupling, no editor mutation, no positions), so a new pipeline needs only to (a) assemble its input node and (b) shape output through `SpeechTransformOptions` - never fork the transform rules (bold tagline, plain former-highlights, stripped un-highlighted, separators, preserved headers). If a pipeline needs a rule the options do not express, extend `SpeechTransformOptions` at the engine, not in the caller.

## ToC bulk-send -> Speech Doc pipeline (`src/blockfile/toc-speech.ts` + `src/screens/BlockFileTocPanel.tsx`)

The **Speech Doc Card Pipelines** PRD, ToC track: a debater ticks the "include this section" checkbox on one or more block-file argument headings in the ToC and clicks **Send to Speech Doc**; every checked section's cards flow, {@link src/speech | Auto Speech}-formatted, onto the *bottom* of the {@link src/speech-doc/active-speech-doc | active speech doc}. It reuses the active-speech-doc contract (PR #83) as the target and the Auto Speech engine (`transformToSpeech`) as the formatter, and is a sibling of the flow-sheet Send Flow pipeline (PR #86). Model re-exported from `src/blockfile`.

- **`sectionSpeechBlocks(editor, checkedPositions, options?)` -> `JSONContent[]` (pure, block-file read-only).** For each checked heading position it gathers that heading's **section** = the heading plus every following sibling in the *same side region* up to the next heading of the **same-or-shallower level** (the `section-ops` boundary contract generalised to any heading level; walking siblings within the heading's own parent means the gather can never cross the `isolating` aff/neg boundary). Overlapping selections (a parent heading and a nested one) de-dup by absolute child position, so each card contributes once. It wraps the collected nodes under a throwaway node - `doc.type.create(null, Fragment.fromArray(items))` (**`create`, never `createChecked`** - skips content-expression validation; the engine only walks structure) - and runs `transformToSpeech`, so the ToC pipeline shares the exact speech shaping (bold tagline, cite, highlighted body flattened, un-highlighted stripped, cards separated, section headers preserved). A checked position that no longer resolves to a heading is skipped, not thrown.
- **`appendBlocksToSpeechBody(speechHandle, blocks, fragment?)` -> count (writes the speech doc only).** Appends block-level document-JSON onto the **end** of the speech doc's `body` fragment through a **short-lived headless editor** (`createEditor` + `editorPreset()`, `insertContentAt(doc.content.size, blocks)`, then `editor.destroy()`) - so the append is an ordinary ProseMirror transaction that flows into the speech doc's `Y.Doc` and persists exactly like a hand-typed edit. This is why the pipeline works even though the target speech doc is usually **not** open in an editor when sending from the block-file screen (the block file and the speech dock are different routes) - it does not require a live editor on the target. A speech doc already open in the split-screen dock converges via Yjs. (Contrast Send Flow, which writes raw `Y.XmlElement` clones because its payload is already Yjs paragraphs; the ToC pipeline's payload is engine JSON, so an editor is the clean JSON->Yjs path.)
- **`sendSectionsToSpeechDoc(blockFileEditor, speechHandle, checkedPositions, options?)` -> `{ sectionCount, blockCount }`** composes both; `sectionCount` counts distinct checked sections that contributed >=1 card. **Non-destructive by construction:** the block file is only read; every write lands in the speech doc's own doc.
- **`BlockFileTocPanel` (`src/screens/`)** is the block-file-specific composition (`BlockFileScreen` renders it in place of a bare `TableOfContents`): owns `useTocSelection`, renders the **Send to Speech Doc** button + `role="status"` line as the ToC `toolbar`, passes `selection` down for the row checkboxes, and runs the pipeline. **No-active-doc / empty-selection = deliberate reversible no-ops, consistent with Send Flow's `SendToSpeechControl`:** button disabled until >=1 heading checked; with no active speech doc the send does nothing and shows "No active speech doc - open or select a speech to send into." with the **selection preserved** so the debater can pick a target (via the dock's active-speech picker) and retry. Reads the `DocumentService` provider-tolerantly (`useContext(DocumentsContext)?.service ?? null`) and the active id via `useActiveSpeechDoc`, so a bare render still paints.
- **Tests:** `src/blockfile/toc-speech.test.ts` is the highest seam (real block-file+card editor + real speech-doc handle over `fake-indexeddb`): checked sections -> formatted append (bold tagline, cite, highlighted-only body, `---` separators, preserved headers), only-checked-sections, **block file unchanged**, **persist across a speech-doc close/reopen**, the nothing-checked no-op, and the stale-position skip; heading positions come from the real `getOutline`. `src/screens/BlockFileTocPanel.test.tsx` drives the panel through the real `DocumentService` (checkbox-per-heading + multi-check, disabled-until-checked, send-appends-and-clears + status, and the no-active affordance with preserved selection). `src/toc/useTocSelection.test.tsx` covers the selection hook.

## Export & Sharing (`src/export/` + `src/export/react/` + `open_external` IPC)

The **Export & Sharing** PRD: a one-click **Export** action on the speech doc and block file surfaces, per-surface payload assembly, and a **pluggable target boundary**.
Email (slice 1/2) and **SpeechDrop (slice 2/2)** both ship, plugging into the same boundary with **no action rework**.
Model re-exported from `src/export`; the React layer from `src/export/react` (kept out of the model index, like `src/formatting/react`).

- **The pluggable target boundary (`target.ts`) is the seam SpeechDrop plugs into with no action change.** Assembly and delivery are two sides of one seam. A surface assembles an `ExportPayload` (`{ subject, html, text }`) - the document rendered **once**, formatting preserved, in every representation a target might need - never knowing *where* it goes. An `ExportTarget` (`{ id, label, export(payload) }`) delivers a payload and returns an `ExportResult` (`{ ok, message, neutral? }`) - never knowing *which surface* built it. Because the payload carries **both** a rich email-friendly HTML document and a structure-preserving plain-text form, a target picks the representation its transport supports (Email drafts from the plain text; a future rich transport sends the HTML) **without assembly changing**. Adding a target = one new object implementing `ExportTarget` + one entry in `DEFAULT_EXPORT_TARGETS` (`email-target.ts`); the `ExportButton` iterates that list, so a second button appears with no other change. **A target must not throw for an expected failure** (missing OS opener, offline transport) - it resolves `{ ok: false, message }` so the action reports it as feedback; throwing is reserved for programmer error. **`neutral: true` marks a deliberate, expected non-delivery** (such as a user cancelling a prompt) - the button shows the message in the muted colour rather than the error colour, since a cancel is not a failure.
- **Payload assembly is per surface, via a short-lived headless editor (`payload.ts`).** The two surfaces have different schemas, so `buildSpeechDocExportPayload(handle, title?)` opens a headless editor over `SPEECH_DOC_BODY_FRAGMENT` with the plain `editorPreset()`, and `buildBlockFileExportPayload(handle, title?)` opens one over `BLOCK_FILE_FRAGMENT` with `blockFileExtensions + cardExtensions` (so card anatomy + body marks serialize) - the same headless-editor pattern as `appendBlocksToSpeechBody`, so export reads only the **handle** and works whether or not the live editor is mounted. Rendering is through the editor's own `DOMSerializer`, so marks come out as the exact semantic HTML the editor renders (`<strong>`/`<mark>`/`<h1>`) - which is what makes the HTML *email-friendly* (no app stylesheet needed). The HTML is wrapped in a complete `<!doctype html>` document; the text is `doc.textBetween(..., "\n\n")` (block structure preserved). Titles fall back to `"Speech"` / `"Block File"`. `buildExportPayload(editor, subject)` is the generic core both wrappers build on.
- **The Email target is `mailto:` through the Tauri boundary (`email-target.ts`), the local-first choice.** No account/SMTP wiring: the target does not *send*, it opens a pre-filled draft in the user's mail client via a `mailto:?subject=…&body=…` URL handed to the OS default handler through the new `open_external` IPC command (`src/ipc.openExternal` -> `src-tauri/src/commands/external.rs`, `std::process::Command` against `open`/`xdg-open`/`cmd /C start`, no plugin/ACL entry needed). **The mailto body is plain text per RFC 6068**, so the draft uses the payload's plain-text form; the rich HTML rides along on the payload for slice 2's richer transport. The transport is injectable (`createEmailTarget(openUrl?)`) so **tests stub it** - `emailTarget` is the app instance wired to the real `openExternal`. **Gotcha - `open_external` has a scheme allowlist (`mailto:`, `https://`, `http://`)**; any other scheme returns `Err` without spawning a process. A future export target that hands off to a different URL scheme must extend `ALLOWED_SCHEMES` in `external.rs`, not reach around it. **Gotcha - `mailtoUrl` uses `encodeURIComponent`, not `URLSearchParams`**, because RFC 6068 requires `%20` for spaces; `URLSearchParams` would emit `+`, which most mail clients cannot decode correctly in the `body` parameter.
- **The action (`react/ExportButton.tsx`) gives non-intrusive feedback.** One button per target ("Export to Email"), plus a `role="status" aria-live` line - the same subtle inline affordance the send controls use, never a modal/toast. It assembles the payload **lazily** on click (`buildPayload: () => ExportPayload | null`; `null` -> a gentle "Nothing to export yet."), hands it to the target, reports the `ExportResult`, and disables while in flight so a double-click can't open two drafts. `BlockFileScreen` and `SpeechDocScreen` each mount one in their header, disabled until the handle is ready. **Gotcha - `SpeechDocScreen` gates on `!handle || !loaded`** (the `loaded` flag from `useDocument`), not just `!handle`; the handle reference is created before IndexedDB finishes loading its content, so gating on `handle` alone would assemble an incomplete payload.
- **Tests (the PRD's highest seams):** `payload.test.ts` (`fake-indexeddb`, real handles) covers per-surface assembly - speech doc heading+bold preserved as semantic HTML + structure-preserving text + subject fallback/escaping, block file card anatomy + `<mark>` body highlight preserved. `email-target.test.ts` covers `mailtoUrl` encoding (+ HTML never smuggled into the body) and success/failure reporting over a **stubbed** `openUrl` (rejection -> `ok:false`, no throw). `react/ExportButton.test.tsx` covers click->assemble->deliver, success + failure feedback, the nothing-to-export no-op, one-button-per-target pluggability, and disabled. `ipc/index.test.ts` covers the `open_external` wrapper (mocked `invoke`). Screen presence is asserted in `BlockFileScreen.test.tsx` and `speech-doc.integration.test.tsx`.

### SpeechDrop target (slice 2/2, `speechdrop-target.ts` + `rtf.ts` + `speechdrop.rs` + `react/`)

The second export target: uploads the document to a [SpeechDrop](https://speechdrop.net) room by code. It plugs into the **same `ExportTarget` boundary** as Email - `ExportButton` is untouched; the two screens just pass `targets={[emailTarget, speechDropTarget]}`. All outbound network goes through a **new Rust command**, mirroring the `open_external` security posture. Model re-exported from `src/export`; React from `src/export/react`.

- **SpeechDrop's real upload flow (reliably determined from its open-source repo `yunyu/SpeechDrop` + live production verification).** A **room code IS the URL slug** (6 case-sensitive unambiguous alphanumerics; the debater types it). The endpoint is **CSRF-protected** (Vert.x `CSRFHandler`), so an upload is **two requests on one cookie jar**: (1) `GET {base}/{room}/index` primes the `XSRF-TOKEN` + `vertx-web.session` cookies (and a 404 here means the room doesn't exist - surfaced as a clear "room code wasn't found"); (2) `POST {base}/{room}/upload` as `multipart/form-data` with the file part, the `X-XSRF-TOKEN` header set to the primed token, and the cookie jar replaying both cookies. Accepted upload MIMEs are document types only (**not `text/html`**): DOC/DOCX/ODT/PDF/RTF/TXT; 10 MB max.
- **Formatting preserved = upload RTF (`rtf.ts`).** Since `text/html` is rejected but `text/rtf` is accepted, the target derives an **RTF** document from the payload's `html` (`htmlToRtf`) - preserving bold/underline/headings/highlight, so debate formatting survives (plain text would lose it). This is a **target-internal choice of representation** (exactly the boundary's intent - "a target picks the representation its transport supports"), **not** a change to payload assembly. `htmlToRtf` walks the known editor HTML subset (`<h1-6>`/`<p>`/`<strong>`/`<em>`/`<u>`/`<mark>`/`<br>`) via `DOMParser`, escapes RTF metacharacters + non-ASCII (`\uN?`), and never drops content (unknown elements still contribute text). Highlight rides a 2-entry color table (`\highlight1` = yellow).
- **The Rust network boundary (`speechdrop.rs`, `speechdrop_upload` command) mirrors `open_external`'s allowlist posture.** `open_external` constrains *what scheme*; this constrains *what host*: the web side **never passes a URL**, only `{ roomCode, fileName, contentType, contentBase64 }`, and the request URL is always built from the fixed `SPEECHDROP_BASE_URL` (`https://speechdrop.net`). `validate_room_code` rejects anything non-alphanumeric (so no path/host injection into the fixed base) and `is_allowed_mime` checks SpeechDrop's own allowlist before any network call. Uses `reqwest` (added dep: `rustls-tls` + `multipart` + `cookies`, no OpenSSL) with a cookie-store client for the two-request CSRF flow; content travels **base64** (binary-safe, future PDF/DOCX unchanged). `classify_upload_response(status, body)` is a **pure** helper (unit-tested) mapping 200→ok, 404→room-not-found, 400 `{err:...}`→bad-type/too-large/no-file. **A future target that must reach a different host adds it here, not by accepting a URL from JS.**
- **Room-code UX + persistence.** The code is prompted **at export time** via a small in-app modal (`SpeechDropRoomPrompt.tsx`, no dialog library, shell-token styled, Escape/backdrop cancel, autofocus+Enter). `useSpeechDropTarget()` (React) wires it: it returns `{ target, prompt }` (the screen renders `{prompt}` once) and the target's injected `promptRoomCode` opens the modal and resolves the promise the export awaits (`null` = cancel = clean no-op). The **last-used code is persisted in `localStorage`** (`speechdrop-room-storage.ts`, key `fulcrum:speechdrop-room`) - per-machine convenience chrome like the dock layout, deliberately **not** Yjs (would sync noise) and not the Rust preference struct (fixed shape); it seeds the next prompt and is written only on a **successful** upload.
- **The model stays React/Tauri-free via two injected seams.** `createSpeechDropTarget({ promptRoomCode, upload, getLastRoomCode?, setLastRoomCode? })` takes the prompt and the `upload` transport as injections, so tests stub both (no network, no React). The app instance injects the real Tauri `uploadToSpeechDrop` (`src/ipc`) and the localStorage seams via `useSpeechDropTarget`. `export()` **never throws for an expected failure** (cancel, empty code, network error, bad room code) - it resolves `{ ok:false, message }`, surfacing the Rust-side message as the same non-intrusive `ExportButton` feedback line. A deliberate cancel additionally sets `neutral: true` so the message renders in the muted colour rather than the error colour.
- **Tests (stubbed transport, per the PRD).** `rtf.test.ts` (formatting/escaping/no-drop); `speechdrop-target.test.ts` (payload correctness - room code, RTF file+mime, formatting preserved; cancel/empty no-ops; **network-failure and bad-room-code** error paths surfaced; success persists the code); `speechdrop-room-storage.test.ts` (round-trip, defaults, best-effort failures); `react/useSpeechDropTarget.test.tsx` (real `ExportButton` over the hook + **stub upload/storage**: prompt→confirm→upload+success, seed from last code, cancel, failure feedback); `ipc/index.test.ts` (the `uploadToSpeechDrop` wrapper). Rust `speechdrop.rs` unit-tests `validate_room_code` (incl. path/host-injection rejection), `is_allowed_mime`, and `classify_upload_response`. **The real network upload can't be unit-tested (no server), matching the flow-DnD precedent - the pure validation/classification + the JS stubbed-transport tests cover the seams; a manual browser/room verification is the remaining check.**

## Sharp edges

- **TypeScript build:** uses two plain `tsc -p ... --noEmit` passes, not project references. Keep `noEmit: true` in both tsconfigs; do not add `references`/`composite` (`tsc -b` errors TS6310/TS6306 with `noEmit`).
- **Rust toolchain** must be on `PATH` for any `tauri` command: `source "$HOME/.cargo/env"` if `cargo` is missing.
- **App icons:** `src-tauri/app-icon.svg` is the source of truth. Regenerate with `npm run tauri icon src-tauri/app-icon.svg`. Keep only the desktop assets: `src-tauri/icons/{32x32,64x64,128x128,128x128@2x}.png`, `icon.icns`, `icon.ico`, `icon.png`.
- **CSP:** `tauri.conf.json` enforces `default-src 'self'`. Inline scripts/styles and all external loads are blocked. Add an explicit CSP directive for any future feature that needs fonts, external images, or eval.
